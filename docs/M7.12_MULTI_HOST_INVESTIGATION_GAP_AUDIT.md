## 1. Executive Summary

Milestone **M7.12 — Multi-Host Investigation** investigates cross-host movement, lateral progression, distributed event correlation, host-aware evidence provenance, and multi-machine forensic analysis across complex enterprise compromise scenarios.

Following a thorough, read-only architectural, source code, database, and test suite inspection across the LogIntel repository:

1. **Foundational Multi-Host Primitive Capabilities Substantially Exist in Earlier Milestones:**
   - **M6.8 (Host Telemetry & Attack Graph Integration):** Implemented `HostGraphBuilder` (`apps/engine/src/logintel/correlation/host_graph.py`), generating host nodes (`host:{hostname}`), process ancestry trees, container bindings, and network socket relationships. Endpoints: `GET /api/v1/investigations/hosts/{host}/graph`, `GET /api/v1/investigations/{incident_id}/host-graph`.
   - **M6.9 (Host Threat Detection & Correlation):** Implemented `HostThreatCorrelator` (`apps/engine/src/logintel/correlation/host_threat.py`) evaluating lateral movement heuristics (`sec.lateral_movement_suspicious_ssh`, `sec.container_escape_attempt`).
   - **M5.10 / Temporal Reconstruction Engine:** Implemented `TemporalReconstructionEngine` (`apps/engine/src/logintel/ai/temporal/reconstruction_engine.py`), featuring explicit `MultiHostTrace` models (`mhost-{case_id}-{idx}`), detecting `TransitionType.HOST_TO_HOST`, cross-host user continuity (`ContinuityType.SAME_ACCOUNT_ACROSS_HOSTS`), and cross-host IP continuity.
   - **M7.2 (Unified Timeline & Replay Engine):** Implemented multi-host timeline indexing (`timeline/service.py:451`), attributing events to `host_id`, indexing timeline items by host (`host_index: Dict[str, List[str]]`), tracking `active_hosts` per replay frame, and providing query filtering by host (`?host=`).
   - **M7.7 (Case Comparison & Campaign Analysis):** Implemented cross-case host overlap detection (`comparison/service.py:267`), correlating shared host entities across distinct investigation cases.

2. **Crucial Functional and Integration Gaps Identified for a Dedicated M7.12 Workflow:**
   - **Gap 1: Explicit Multi-Host Case Scoping:** In `InvestigationScope` (`apps/engine/src/logintel/ai/domain/workspace.py`), scope targets are defined via `selected_entity_ids` and `subject_id`. While `timeline/service.py` attempts to read `getattr(case.scope, "target_hosts", [])`, the model does not formally define `target_hosts: List[str]`, causing it to default to `[]` or `"unknown-host"`.
   - **Gap 2: Missing Dedicated Multi-Host Investigation Workspace UI:** While multi-host lateral traces are rendered inside a sub-tab of `InvestigationTemporalExplorer.tsx` (lines 844–890) and individual hosts can be filtered on `InvestigationUnifiedTimeline.tsx`, there is no top-level or primary workbench dedicated specifically to side-by-side multi-host comparative triage, cross-host event pivoting, or host fleet inventory exploration within a case.
   - **Gap 3: Missing Dedicated Multi-Host API Namespace:** Host operations are scattered across `/investigations/hosts/{host}/graph`, `/cases/{id}/timeline/unified?host=`, and `/cases/{id}/timeline/reconstruction` rather than a unified REST namespace (e.g. `/cases/{id}/hosts`).
   - **Gap 4: Incomplete Host Discovery & Registry Integration:** The database table `hosts` in `logintel.db` contains basic metadata (`id`, `hostname`, `os_name`, `os_version`, `first_seen`, `last_seen`), but lacks dynamic case-association tables or cross-host network topology mapping.

## 6. API and Database Reality

### 6.1 Database Verification
- `PRAGMA integrity_check` on `logintel.db` and `cases.db`: Both return `ok`.
- `hosts` table in `logintel.db`: Contains 1 local host record (`id: 2ec0288935e3729a`, `hostname: Khemendra-labs`).
- `events.host`: Ingested events carry individual host attributions.
- Schema Migrations: Strictly frozen at 5. No new migrations required or permitted. Existing schemas in `cases.db` can fully accommodate multi-host scope metadata via `scope_json`.

### 6.2 API Gaps
- Currently, an analyst inspecting a case must query `GET /cases/{case_id}/timeline/reconstruction` to obtain `multi_host_traces`, then individually query `/investigations/hosts/{host}/graph` for each host, and query `/cases/{case_id}/timeline/unified?host={host}` for each host's timeline.
- **Architectural Need:** A dedicated, case-scoped endpoint `GET /api/v1/cases/{case_id}/hosts` returning:
  1. Participating hosts in the case (extracted from evidence references, alerts, and scope).
  2. Per-host event and alert counts.
  3. First-seen and last-seen activity timestamps per host.
  4. Inbound and outbound lateral transitions involving each host.
  5. Missing host visibility telemetry gaps.

   - Multi-host analysis is fragmented between the timeline filter and an obscure sub-tab of the AI temporal panel.
   - No dedicated visual comparison showing how an attack progressed from Host A to Host B across time (e.g. synchronized swimlanes or comparative event tables).
   - No one-click action to pivot from a lateral trace directly into host-specific telemetry or graphs.
