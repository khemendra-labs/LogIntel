## 5. PERSISTENT CASE ARCHITECTURE

The M5.5 architectural model strictly decouples authoritative forensic evidence from mutable analyst case state:

```text
AUTHORITATIVE FORENSIC STATE (logintel.db)
        │
        │ [Read-Only Resolution via CaseEvidenceReference]
        ▼
PERSISTENT ANALYST CASE (cases.db)
        │
        ├── investigation_cases (lifecycle state, owner, scope, version)
        ├── case_hypotheses (analyst hypotheses, evidence tags, status)
        ├── case_evidence_references (source pointer, citation tag, status)
        ├── case_query_history (governed query templates, parameters, results)
        ├── case_reports (versioned drafts, analyst notes, AI provenance)
        └── case_audit_log (append-only ledger protected by SQLite triggers)
        │
        ▼ [On-Demand Deterministic Reconstruction]
LOCAL AI ADVISORY CONTEXT (Episodic, Stateless)
        │
        ▼
ANALYST DECISION & REPORTING
```

Key architectural guarantees:
- **No Payload Duplication:** Authoritative raw forensic payloads (`raw_message`, `event_fingerprint`, etc.) are never cloned into `cases.db`. Evidence is stored exclusively as references (`source_type`, `source_id`).
- **Dynamic Resolution:** Evidence references are resolved dynamically against `logintel.db` at query time. Missing or purged events are identified as `MISSING` or `UNRESOLVED`.
- **Zero AI Memory Leakage:** AI advisory context is generated dynamically from the active case state. There are no cross-case chat histories, no vector databases, no embeddings, and no persistent AI memory.

## 6. CASE LIFECYCLE

Cases follow a deterministic finite state machine enforced at the application boundary and stored in `cases.db`:

```text
       ┌───────────┐
       │   OPEN    │
       └─────┬─────┘
             │
             ▼
       ┌───────────┐         ┌───────────┐
       │  ACTIVE   │ ◄─────► │  PAUSED   │
       └─────┬─────┘         └───────────┘
             │
             ▼
 ┌───────────────────────┐
 │   READY_FOR_REVIEW    │
 └───────────┬───────────┘
             │
             ▼
       ┌───────────┐
       │  CLOSED   │
       └─────┬─────┘
             │
             ▼
       ┌───────────┐
       │ ARCHIVED  │
       └───────────┘
```

Valid transitions:
- `OPEN` → `ACTIVE`, `CLOSED`, `ARCHIVED`
- `ACTIVE` → `PAUSED`, `READY_FOR_REVIEW`, `CLOSED`, `ARCHIVED`
- `PAUSED` → `ACTIVE`, `CLOSED`, `ARCHIVED`
- `READY_FOR_REVIEW` → `ACTIVE`, `CLOSED`, `ARCHIVED`
- `CLOSED` → `ACTIVE` (reopen), `ARCHIVED`
- `ARCHIVED` → `ACTIVE` (unarchive), `CLOSED`

Invalid transitions (e.g. `OPEN` → `PAUSED`, `CLOSED` → `PAUSED`) raise explicit `ValueError` exceptions and are rejected. Every valid transition increments the case version and records an audit log entry.

## 7. EVIDENCE REFERENCE MODEL

Rather than copying forensic records, cases maintain lightweight references:

```json
{
  "reference_id": "ref-410a82",
  "case_id": 101,
  "source_type": "event",
  "source_id": "ev-auth-999",
  "citation_tag": "[event:ev-auth-999]",
  "role": "SUPPORTING",
  "epistemic_status": "OBSERVED",
  "resolution_status": "AVAILABLE",
  "analyst_annotation": "Sudo authentication failure event",
  "created_at": "2026-10-02T12:00:00Z"
}
```

Resolution semantics:
- When the referenced record exists in `logintel.db`, `resolution_status` resolves to `AVAILABLE` and `resolved_record` is populated dynamically.
- If the referenced record has been purged or does not exist, `resolution_status` resolves to `MISSING` and `resolved_record` is `null`. Stale evidence is thus explicitly visible to the analyst without corrupting case history.

## 8. HYPOTHESIS PERSISTENCE

Analyst hypotheses are persistent first-class entities with independent versioning, status lifecycles, and evidence associations:

- **Statuses:** `OPEN`, `SUPPORTED`, `WEAKENED`, `UNRESOLVED`, `REJECTED`.
- **Evidence Linking:** Explicitly tagged with supporting and contradicting citation tags (`[event:...]`, `[alert:...]`).
- **Gaps:** Explicit list of investigative unknowns (`evidence_gaps`) requiring threat hunting or additional data.
- **Analyst Assessment:** Preserves human analyst notes, which AI assistance cannot overwrite.

## 9. QUERY HISTORY

Threat hunting queries executed from a case are governed and recorded in `case_query_history`:

- **Governed Templates:** Queries are restricted to authorized parameter-bound templates (e.g. `query_failed_logins_by_user`, `query_process_events_by_exe`).
- **No Arbitrary SQL:** Raw SQL queries from the UI or AI are rejected.
- **Traceability:** Records `query_template_id`, bound `parameters`, analyst `rationale`, executing `actor`, `result_count`, and execution timestamp.

## 10. AI CONTEXT RECONSTRUCTION

Local AI advisory operations do not possess persistent conversational memory across cases. Instead, context is reconstructed deterministically from explicit persistent case state:

```text
Investigation Case State (cases.db)
  ├── Scope (hosts, timeframe, alerts)
  ├── Resolved Evidence Records
  ├── Active Hypotheses & Evidence Gaps
  ├── Query History Summary
  └── Latest Report Findings
        │
        ▼
Structured AI Context Assembly (Episodic)
        │
        ▼
Local Ollama Request (Strict Epistemic Prompting)
        │
        ▼
Structured Output Validation & Citation Check
```

This guarantees:
1. Re-running AI analysis on identical case state produces reproducible advisory output.
2. No cross-case information leakage can occur, as each request is built strictly from the isolated case state.
3. No external embeddings or vector databases are utilized.

## 11. AI CONTENT PROVENANCE

All report versions, findings, and hypotheses clearly identify content origin:

- `ContentOrigin.AI_GENERATED`: Generated by the local AI engine with attached `model_id` (e.g., `qwen2.5:0.5b`), deterministic `model_digest`, and context version.
- `ContentOrigin.ANALYST_AUTHORED`: Authored or revised by the human analyst.
- `ContentOrigin.SYSTEM_GENERATED`: Synthesized by core correlation or rule engine.

AI regeneration cannot silently overwrite analyst-authored sections. Analyst notes and revisions are preserved in new versions.

## 12. REPORT VERSIONING

Investigation reports support append-only versioning:

- Version counter increments deterministically (`version = 1, 2, 3...`).
- Historical versions remain permanently readable and immutable.
- Version diff comparisons (`/api/v1/cases/{id}/reports/{rid}/diff?v1=1&v2=2`) compare executive summaries, fact counts, hypothesis updates, and analyst notes.
- Marking a report `is_final = true` preserves final sign-off state.
