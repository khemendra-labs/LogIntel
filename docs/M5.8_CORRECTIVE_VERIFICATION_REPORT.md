## 4. Confidence / Corroboration Semantic Verification

### Epistemic Status vs Corroboration Status

To comply strictly with M58-07 ("Strength Without Fake Scores") and eliminate probabilistic or synthetic confidence metrics, LogIntel maintains an authoritative architectural boundary between **Epistemic Classification** and **Corroboration Status**:

```
+-----------------------------------------------------------------------------------+
|                              GRAPH RELATIONSHIP EDGE                              |
+---------------------------------------------------------+-------------------------+
| EPISTEMIC CLASSIFICATION (Knowledge Provenance)         | CORROBORATION STATUS    |
| (What is the ontological ground of this edge?)          | (How well supported?)   |
+---------------------------------------------------------+-------------------------+
| OBSERVED: Directly recorded in authoritative telemetry   | DIRECT_OBSERVATION      |
| INFERRED: Deduced deterministically via rule/hunt logic  | DIRECT_EVIDENCE         |
| UNKNOWN:  Candidate relationship pending evidence       | CORROBORATED            |
|                                                         | SINGLE_SOURCE           |
|                                                         | TEMPORALLY_ALIGNED      |
|                                                         | CONTRADICTED            |
|                                                         | INSUFFICIENT_EVIDENCE   |
|                                                         | UNRESOLVED              |
+---------------------------------------------------------+-------------------------+
```

### Supported Corroboration Statuses

1. **`DIRECT_OBSERVATION` / `DIRECT_EVIDENCE`:**
   * **Meaning:** The relationship is explicitly documented in primary authoritative telemetry (e.g., SSH authentication record linking user and source IP).
   * **Authoritative:** Yes (`is_authoritative = True`).
   * **Epistemic:** `OBSERVED`.
2. **`CORROBORATED`:**
   * **Meaning:** Supported by multiple distinct forensic evidence sources (e.g., network flow connection AND syslog process execution event).
   * **Authoritative:** Depends on source records.
   * **Epistemic:** `OBSERVED` or `INFERRED`.
3. **`SINGLE_SOURCE`:**
   * **Meaning:** Supported by exactly one event or detection without independent corroboration.
   * **Authoritative:** Yes (if from authoritative telemetry) or No (if hypothetical).
   * **Epistemic:** `OBSERVED` or `INFERRED`.
4. **`TEMPORALLY_ALIGNED`:**
   * **Meaning:** Entities interacted within an active incident correlation time window, but direct causality is inferred.
   * **Authoritative:** No.
   * **Epistemic:** `INFERRED`.
5. **`CONTRADICTED`:**
   * **Meaning:** Relationship is contradicted by chronological or authoritative evidence (e.g., event timestamp occurs prior to user account creation).
   * **Authoritative:** Deterministic derivation.
   * **Epistemic:** `INFERRED` / `UNKNOWN`.
6. **`INSUFFICIENT_EVIDENCE` / `UNRESOLVED`:**
   * **Meaning:** Hypothesized or candidate relationship lacking sufficient telemetry for confirmation.
   * **Authoritative:** No.
   * **Epistemic:** `UNKNOWN`.

## 5. Investigation Graph Verification

The M5.8 investigation graph architecture was validated against the following criteria:
* **Derived Intelligence:** The graph is built dynamically on demand from underlying authoritative tables (`incidents`, `incident_entities`, `incident_relationships`, `alerts`, `detections`, `events`) and governed case data in `cases.db`. It never modifies forensic sources of truth.
* **Deterministic Provenance:** Every graph edge contains an `evidence_references` list and `evidence_event_ids` linking directly to specific canonical records.
* **Traversal & Path Search:** Breadth-first search (BFS) path finding between source and target entities operates with bounded depth ($\le 10$) and cycle prevention.
* **Temporal Sequencing:** Graph edges are chronologically sequenced with relative time offsets (`delta_seconds_from_incident_start`), preserving causal ordering.
* **Serialization Formats:** Supports JSON graph export (nodes, edges, metadata) and GraphML XML export with CDATA-escaped attributes for external visualization tools.

* **M58-SEC-010 (Memory Boundedness):** Large graph requests enforce memory and response size safety.
* **M58-SEC-011 (GraphML XML CDATA Injection):** XML serialization safely encodes CDATA markers (`]]>`) and control characters.
* **M58-SEC-012 (GraphML Attribute Sanitization):** Attribute values in GraphML export are strictly escaped.
* **M58-SEC-013 (JSON Export Sanitization):** JSON graph export enforces RFC 8259 compliance without unescaped control codes.
* **M58-SEC-014 (Audit Logging on Access):** Case audit log records every graph retrieval and export action.
* **M58-SEC-015 (Advisory AI Containment):** AI graph explanations are strictly advisory and cannot alter graph state.
* **M58-SEC-016 (Prompt Injection Containment):** Malicious telemetry within graph nodes cannot hijack AI explanation prompts.
* **M58-SEC-017 (No Shell / Subprocess Execution):** Graph operations execute zero shell commands or subprocess invocations.
* **M58-SEC-018 (Localhost Network Binding):** API operations bind strictly to `127.0.0.1`.
* **M58-SEC-019 (Path Traversal Prevention):** Case ID and export format parameters reject directory traversal sequences (`../../`).
* **M58-SEC-020 (Owner-Private File Permissions):** `cases.db` (0600) and parent directory (0700) permissions remain intact.
