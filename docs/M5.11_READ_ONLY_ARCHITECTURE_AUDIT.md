## 2. Architecture Audit Checklist (Questions 1 to 10)

### 1. What Already Exists?
- **Forensic Storage (`logintel.db`):** Authoritative tables for `events`, `detection_rules`, `alerts`, `detections`, `detection_evidence`, `incidents`, `incident_entities`, `incident_relationships`, `investigation_notes`, and `investigation_notes_audit`.
- **Investigation Workspace (`cases.db`):** Tables for `investigation_cases`, `case_hypotheses`, `case_evidence_references`, `case_query_history`, `case_reports`, `case_audit_log`, `case_finding_reviews`, and `case_transition_reviews`.
- **Investigation Graph Engine (M5.8):** `InvestigationGraphBuilder` constructing nodes and edges with corroboration and epistemic states.
- **Evidence Correlation Engine (M5.9):** `EvidenceCorrelationEngine` generating clusters, behavioral sequences, and gap analyses.
- **Temporal Reconstruction Engine (M5.10):** `TemporalReconstructionEngine` generating episodes, transitions, multi-host traces, and attack sequences.
- **Local AI Advisory:** Context assembler and advisory prompt runners returning non-authoritative explanations.
- **Authentication & Governance:** Bearer token authentication and bounded query clamping across all case routes.

### 2. What Can Be Reused?
- **Case Evidence Resolution:** `case.evidence_references` and `case_service.associate_evidence` provide verified linkage to forensic telemetry.
- **Hypothesis Engine:** `case_hypotheses` table and hypothesis analysis routines in `case_service.py` provide support/contradiction tracking.
- **Temporal Reconstruction:** `get_temporal_reconstruction` provides episodes, transitions, gaps, and attack sequence steps.
- **Report Infrastructure:** `case_reports` table in `cases.db` already supports immutable report versioning, executive summary, facts, inferences, unknowns, and recommendations.
- **Finding Reviews:** `case_finding_reviews` table in `cases.db` already stores analyst reviews without touching `logintel.db`.

### 3. What Is Missing for M5.11?
- **Case Assessment Model (`CaseAssessment`):** Comprehensive evaluation aggregating evidence sufficiency, key findings, competing hypotheses, gaps, and closure readiness.
- **Evidence Sufficiency Analysis:** Categorical evaluation (`SUFFICIENT`, `PARTIALLY_SUFFICIENT`, `INSUFFICIENT`, `UNKNOWN`) explaining what is proved, missing, or contradictory.
- **Competing Hypothesis Framework:** Multi-hypothesis assessment side-by-side without forcing a single narrative.
- **Investigation Questions Table & Domain (`case_investigation_questions`):** Structured questions (`OPEN`, `INVESTIGATING`, `ANSWERED`, `UNRESOLVED`) with recommended queries.
- **Evidence Gap Prioritization:** Categorical severity (`CRITICAL`, `HIGH`, `MEDIUM`, `LOW`) with causal explanations.
- **Deterministic Closure Readiness Evaluation:** Verification against unreviewed findings, open questions, critical gaps, and contradictory evidence.
- **Analyst Assessment vs System Analysis Separation:** Clear demarcation of `SYSTEM_DETERMINISTIC`, `LOCAL_AI_ADVISORY`, and `ANALYST_AUTHORED` content origins.
- **Evidence-Backed Conclusion Model:** Formal statements bound to supporting evidence, limitations, and explicit unknowns.
- **Investigation Briefing Generator:** Evidence-derived briefing covering all 15 required sections.
- **Structured Case Handoff:** Package assembling summary, findings, gaps, and required next steps for transfer between analysts.
- **Desktop UI Component (`InvestigationAssessmentExplorer.tsx`):** Front-end workbench exposing assessment, sufficiency, findings, hypotheses, questions, briefing, and report drafting.

### 4. What Must Remain Immutable?
- **Forensic Telemetry:** Events, raw logs, detection rules, alerts, detections, and detection evidence in `logintel.db` must never be altered or deleted.
- **Historical Report Versions:** Reports in `case_reports` must never be overwritten or deleted; each revision creates a new monotonically increasing version.
- **Epistemic States:** Forensic truth (`OBSERVED`, `INFERRED`, `UNKNOWN`) must never be modified by analyst acceptance (`ACCEPTED`).

### 5. Can M5.11 Be Implemented Without Migration 6?
**YES.**
All M5.11 case assessments, analyst notes, questions, and handoff metadata belong exclusively to `cases.db` (the analyst workspace database). `logintel.db` requires zero schema changes. Migration 6 will remain strictly at 0.

### 6. What Belongs in `cases.db`?
- `case_assessments`: Stores overall assessment state, evidence sufficiency, closure readiness, and analyst-authored conclusions.
- `case_investigation_questions`: Stores structured investigative questions, statuses, and recommended queries.
- `case_finding_reviews`: Existing table for analyst finding reviews.
- `case_reports`: Existing table for immutable report versions and briefings.
- `case_audit_log`: Existing immutable audit log of all case state transitions.

### 7. What Must Never Enter `logintel.db`?
- Analyst subjective notes or speculative hypotheses.
- AI-generated narratives, advisory briefings, or prompt explanations.
- Case-specific workflow state or review dispositions.
- Transient threat hunt proposals or investigative questions.

## 3. Scope Boundary & Anti-Patterns To Forbid

| Forbidden Pattern | Strict M5.11 Constraint |
| :--- | :--- |
| **Numeric Confidence / Risk Scores** | No `87% confidence` or `risk_score = 0.92`. Only categorical states (`SUFFICIENT`, `PARTIALLY_SUFFICIENT`, `INSUFFICIENT`, `UNKNOWN`). |
| **Automatic Incident Closure** | Closure readiness is advisory only (`READY`, `NOT_READY`). Final closure requires explicit analyst action. |
| **AI Rewriting Truth** | AI cannot generate authoritative findings or alter epistemic status. `is_authoritative = False` everywhere. |
| **Review Conflation** | `INFERRED + ACCEPTED` remains `INFERRED`. Review state is separate from forensic epistemic state. |
| **Migration 6** | `logintel.db` must not be touched. All analytical metadata resides in `cases.db`. |
| **External Network / Cloud AI** | Zero outbound calls. Local Ollama loopback only. Zero shell/subprocess execution. |
