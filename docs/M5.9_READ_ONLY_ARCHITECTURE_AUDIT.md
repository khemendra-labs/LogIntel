## 1. Current Architecture

LogIntel currently operates a layered, forensic-first investigation system with a strict trust hierarchy:

```text
RAW TELEMETRY (/var/log/syslog, auth.log, journald)
        ↓
CANONICAL FORENSIC EVENTS (events table in logintel.db)
        ↓
DETECTIONS & OPERATIONAL ALERTS (alerts, detections in logintel.db)
        ↓
CORRELATED SECURITY INCIDENTS (incidents, incident_entities, incident_relationships)
        ↓
PERSISTENT INVESTIGATION CASES (cases.db: cases, hypotheses, evidence references, reports, audit log)
        ↓
EVIDENCE-BOUND INVESTIGATION GRAPH (M5.8: InvestigationGraphBuilder, BFS paths, temporal chains, pivots)
        ↓
ANALYST WORKBENCH & ADVISORY LOCAL AI (Advisory-only Ollama runtime @ 127.0.0.1:11434)
```

The system is separated into:
* **`logintel.db` (Authoritative Forensic Store):** Read-only during investigations. Contains canonical events, detection rules, alerts, detections, and incident correlations. Migrations 1–5 applied; Migration 6 is strictly absent.
* **`cases.db` (Investigation Governance Store):** Owner-private (`0600`) SQLite database with append-only audit log enforced by database triggers (`trg_prevent_case_audit_update`, `trg_prevent_case_audit_delete`, `trg_prevent_case_delete`, etc.). Stores case state, analyst hypotheses, evidence references, report versions, and finding reviews.
* **Engine Core (`apps/engine/`):** FastAPI IPC service with Bearer token authentication, repository abstractions, deterministic correlator, investigation intelligence service, and local AI provider integration.
* **Desktop Client (`apps/desktop/`):** React 18 + TypeScript + Vite desktop UI operating within a Tauri shell.

## 5. Data-Flow Changes

1. **Graph-to-Correlation Ingestion:** The correlation engine consumes the constructed `InvestigationGraph` alongside case evidence references.
2. **Deterministic Clustering:** Nodes and edges sharing multi-attribute criteria (temporal bounds, shared entities, explicit evidence links) are synthesized into `EvidenceCluster` instances.
3. **Hypothesis Evaluation:** Each `AnalystHypothesis` is mapped against the evidence clusters to isolate supporting, contradicting, and missing evidence.
4. **Governed Hunt Feedback Loop:** Evidence gaps generate recommended query proposals (`GovernedThreatHuntProposal`) that an analyst can review, approve, and execute.
5. **Advisory Explanation:** Local AI receives strictly structured JSON context containing cluster nodes, edges, reasons, and citations, returning natural-language briefings with verified citation boundaries.

## 6. Persistence Boundary

* **Authoritative Immutability (`logintel.db`):** 100% read-only. Zero writes, zero mutations, zero schema changes.
* **Governed Case Persistence (`cases.db`):**
  * Existing tables (`investigation_cases`, `case_hypotheses`, `case_evidence_references`, `case_query_history`, `case_reports`, `case_audit_log`, `case_finding_reviews`) remain authoritative for analyst annotations.
  * Finding reviews are saved using the existing `case_finding_reviews` table.
  * Audit log triggers continue to enforce append-only immutability.
* **In-Memory Derived Intelligence:** Evidence clusters, temporal sequence analyses, and correlation graphs are derived on demand from underlying authoritative records. This eliminates redundant data duplication and avoids schema drift.

6. `POST /api/v1/cases/{case_id}/correlation/findings/generate` — Deterministically generate structured investigation findings from verified clusters.
7. `GET /api/v1/cases/{case_id}/correlation/workbench/{entity_type}/{entity_value}` — Comprehensive entity-centric investigation workbench dossier.
8. `POST /api/v1/cases/{case_id}/correlation/explain` — Advisory local AI correlation briefing and decision support synthesis.

## 8. Security Implications

* **Authentication & Authorization:** All M5.9 endpoints enforce Bearer token verification via `verify_engine_token`.
* **Case Isolation:** Queries strictly filter by `case_id`; cross-case data leakage is prevented.
* **Input Validation & Parameterization:** Entity keys, cluster IDs, and hypothesis IDs are sanitized. No raw SQL concatenation.
* **Query Bounding:** Cluster size capped at $\le 100$ items, traversal depth capped at $\le 5$ hops.
* **Execution Bounds:** Threat hunts execute strictly through allowlisted parameterized templates (`search_auth_failures`, `search_process_exec`, etc.). Arbitrary SQL and shell commands remain prohibited.
* **Provenance Verification:** All generated findings and clusters link directly to SHA-256 hashes of primary records.

---

## 9. AI Boundary

* **Advisory Only:** Local AI cannot create, update, or delete clusters, findings, cases, or database records.
* **Prompt Injection Containment:** Telemetry within clusters (usernames, commands, file paths) is wrapped in XML CDATA envelopes and treated as data.
* **No Direct DB Access:** AI receives pre-assembled, filtered JSON context; no raw connection strings or execution privileges.
* **Localhost Daemon:** Binds exclusively to `127.0.0.1:11434`.

## 11. Performance Risks & Mitigations

* **Risk:** Pairwise $O(N^2)$ correlation across thousands of evidence records.
  * *Mitigation:* Strict case-evidence bounding ($\le 200$ records per case scope), indexed entity lookups, and early pruning on temporal distance (> 3600s).
* **Risk:** Deep behavioral graph recursion.
  * *Mitigation:* Cycle detection via visited sets; depth clamping ($\le 5$).
* **Target:** All core correlation and cluster construction operations complete under 15 ms median on local workstation benchmarks.

## 15. Risks & Challenges

1. **Complexity in Multi-Dimensional Clustering:** Combining temporal proximity with shared entity overlap can produce noisy clusters if thresholds are too loose.
   * *Control:* Explicit minimum criteria: at least 2 distinct attributes or 1 authoritative link + tight temporal proximity ($\le 300$s).
2. **Distinguishing Epistemic vs Review States:** Analysts may confuse a finding's epistemic status (`INFERRED`) with their decision to accept it (`ACCEPTED`).
   * *Control:* Separate UI columns and domain model fields for `epistemic_status` and `review_status`.
