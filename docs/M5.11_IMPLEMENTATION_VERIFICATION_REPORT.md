## 2. Operating Principle & Scope Boundaries

### Operating Principle
> **"LogIntel must help an analyst connect evidence, not manufacture certainty."**

LogIntel never claims forensic completeness where telemetry is missing or ambiguous. System determinations are categorized into transparent epistemic tiers and accompanied by explainable rationales and actionable remedies.

### Strict Scope Boundaries
* **Zero Cloud AI / External Dependencies:** No OpenAI, Anthropic, Gemini, external vector databases, remote embeddings, RAG pipelines, or persistent AI memory.
* **Zero Autonomous Action:** The platform does NOT close cases automatically, execute remediation scripts, modify system state, or dispatch containment actions without explicit human analyst confirmation.
* **Zero Shell / Subprocess Execution:** AI advisory endpoints and assessment generators execute purely in-process Python logic without spawning bash/shell subshells or executing external binaries.
* **Strict SQL Guardrails:** No dynamic raw SQL concatenation from user input. Queries use parameterized statements or predefined governed query templates.
* **Strict Bounded Payloads:** Maximum 50 findings, 50 questions, 50 evidence gaps, 10 hypotheses, 20 evidence citations per item, and maximum report sizes clamped at 1 MB.

## 4. Epistemic Separation & No-Fake-Confidence Architecture

LogIntel enforces a strict distinction between **Epistemic Classification** (what forensic telemetry actually proves) and **Analyst Review State** (the analyst's operational disposition toward a finding):

```
+-----------------------------------------------------------------------------------+
|                            EPISTEMIC GROUND TRUTH                                 |
|  [OBSERVED]                [INFERRED]                     [UNKNOWN]               |
|  Directly witnessed in     Synthesized across transitions Indeterminate, missing, |
|  authoritative logs        or temporal continuity         or telemetry gap        |
+-----------------------------------------------------------------------------------+
                                         |
                                         | Evaluated by human analyst
                                         v
+-----------------------------------------------------------------------------------+
|                             ANALYST REVIEW STATE                                  |
|  [UNREVIEWED]              [ACCEPTED]                     [REJECTED] / [DISPUTED] |
|  Default pending human     Endorsed by analyst for        Challenged or deemed    |
|  verification              inclusion in conclusion        non-corroborated        |
+-----------------------------------------------------------------------------------+
```

### Invariant Rules
1. `OBSERVED` requires direct evidence references in canonical forensic logs (`events`, `alerts`, `incidents`).
2. `INFERRED` represents logical derivations across transitions, attack sequences, or continuities.
3. When an analyst reviews an `INFERRED` finding and sets `review_state = ACCEPTED`, the finding's `epistemic_status` remains `INFERRED`. It NEVER converts to `OBSERVED`.
4. No numerical confidence percentages, probabilities, or synthetic risk scores are permitted anywhere in the data model or frontend.

## 7. Evidence Sufficiency Evaluation Engine

Implemented in `AssessmentEngine.evaluate_evidence_sufficiency`:
* **Categorical State Mapping:**
  * $\ge 5$ evidence references, $\ge 1$ observed finding, and 0 critical gaps $\rightarrow$ `SUFFICIENT`
  * $\ge 2$ evidence references and no critical telemetry gaps $\rightarrow$ `PARTIALLY_SUFFICIENT`
  * Critical gaps unresolved or $< 2$ evidence references $\rightarrow$ `INSUFFICIENT`
  * Empty evidence catalog $\rightarrow$ `UNKNOWN`
* **Missing & Contradicting Evidence:** Automatically detects unexplained authentication failures followed by root execution without intervening privilege escalation as missing authorization telemetry.

## 8. Key Findings Synthesis Engine

Implemented in `AssessmentEngine.synthesize_key_findings`:
* Ingests pinned case evidence references (`[event:...]`, `[alert:...]`, `[incident:...]`) and temporal transitions (`STAGE_PROGRESSION`, `PRIVILEGE_ESCALATION`, `LATERAL_MOVEMENT`, `PERSISTENCE_ESTABLISHED`).
* Assigns `epistemic_status`:
  * Direct event citations $\rightarrow$ `OBSERVED`
  * Inferred multi-step transitions or multi-host traces $\rightarrow$ `INFERRED`
  * Uncorroborated gaps or unverified queries $\rightarrow$ `UNKNOWN`
* Applies existing analyst review overrides from `case_finding_reviews` table.
* Caps finding output at 50 to guarantee bounded computation.

## 9. Analyst Review Workflow & Immutability

Analysts can review any finding by transitioning its review state:
`UNREVIEWED` $\rightarrow$ `ACCEPTED`, `REJECTED`, or `DISPUTED`.

* **Immutability Contract:** Mutating review state updates `review_state`, `reviewed_by`, `reviewed_at`, and `review_notes`. It **never** alters `epistemic_status`.
* **Audit Trail:** Every transition is recorded in `case_audit_log` with actor, timestamp, previous state, new state, and rationale.

## 10. Competing Hypotheses Assessment Engine

Implemented in `AssessmentEngine.assess_hypotheses`:
Evaluates multiple competing hypotheses side-by-side against available evidence:
1. **Malicious External Compromise:** Supported by external IP connections, brute force attempts, and unauthorized privilege escalation.
2. **Authorized Administrative Activity:** Evaluated against authorized change window criteria and authenticated service accounts.
3. **Internal System Misconfiguration:** Evaluated when failed events lack lateral movement or persistence indicators.

Each hypothesis produces an evidence-grounded determination: `SUPPORTING`, `CONTRADICTING`, or `UNRESOLVED`.

## 11. Prioritized Evidence Gaps & Actionable Remedies

Implemented in `AssessmentEngine.prioritize_evidence_gaps`:
* Converts chronological telemetry pauses and missing transition edges into `PrioritizedEvidenceGap` items.
* Prioritizes gaps categorically:
  * Missing root execution or lateral pivot logs $\rightarrow$ `CRITICAL`
  * Long telemetry gaps ($> 30$ minutes) during active episodes $\rightarrow$ `HIGH`
  * Uncorroborated user-agent or secondary metadata $\rightarrow$ `MEDIUM`
* Supplies concrete, non-destructive SQL hunting query suggestions for analysts to run locally in the hunting console.

## 13. Advisory Closure Readiness Evaluation

Implemented in `AssessmentEngine.evaluate_closure_readiness`:
* Evaluates 5 categorical gating criteria:
  1. Are there unreviewed findings? (Blocking)
  2. Are there unresolved `CRITICAL` evidence gaps? (Blocking)
  3. Is evidence sufficiency rated `INSUFFICIENT`? (Blocking)
  4. Are there unresolved open questions? (Warning)
  5. Are there contradicting evidence items? (Warning)
* Categorical readiness output:
  * If blocking factors exist: `NOT_READY`
  * If only warnings exist: `READY_WITH_LIMITATIONS`
  * If all criteria satisfied: `READY`
* **Non-Autonomous Invariant:** Advisory only. Does NOT automatically change case status or close incidents.
