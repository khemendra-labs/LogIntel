### 1. Existing Investigation Lifecycle
* **Current Model:** In Milestone 4, investigations are centered around correlated `incidents` (`apps/engine/src/logintel/models/incidents.py`).
* **Lifecycle States:** `IncidentStatus` supports `OPEN`, `TRIAGED`, `INVESTIGATING`, `CONTAINED`, `CLOSED`, `FALSE_POSITIVE`. State transitions are strictly validated by `ALLOWED_STATUS_TRANSITIONS` in `incidents_repo.py`.
* **M5.4 Requirement:** An analyst-centric investigation workspace lifecycle:
  ```text
  OPEN → ACTIVE → PAUSED → READY_FOR_REVIEW → CLOSED
  ```
* **Audit Finding:** The investigation lifecycle can be managed at the investigation workspace layer, referencing the underlying incident while introducing explicit analyst workflow states. AI is strictly barred from transitioning states.

---

### 2. Investigation State Model
* **Current Structure:** The `incidents` table tracks incident metadata, timestamps, primary entities, and operational alert counts.
* **M5.4 Requirement:** Deterministic investigation state machine with validated transitions, transition timestamps, analyst attribution, and reason logging.
* **Audit Finding:** Can be implemented in an `InvestigationWorkspace` domain model that tracks `state: InvestigationState`, `scope: InvestigationScope`, `hypotheses: List[AnalystHypothesis]`, `evidence_candidates: List[EvidenceItem]`, `notes: List[InvestigationNote]`, and `audit_trail: List[InvestigationStateAudit]`.

---

### 3. Evidence References
* **Current Structure:** Telemetry and graph entities are referenced via canonical bracketed citation tags:
  * `[event:<id>]`: Canonical event from `events` table
  * `[alert:<id>]`: Operational alert from `alerts` table
  * `[entity:<key>]`: Correlated entity from `incident_entities`
  * `[step:<num>]`: Attack progression step from attack path reconstruction
  * `[mitre:<id>]`: Authoritative MITRE mapping established in M4
* **Audit Finding:** All citation tags retain strict provenance: `source_table`, `source_id`, `evidence_id`, `timestamp`, `role`.

---

### 4. Evidence Bundle
* **Current Structure:** `InvestigationEvidenceBundle` (`apps/engine/src/logintel/ai/domain/bundle.py`) coordinates multi-dimensional evidence across all 7 entity types (`HOST`, `USER`, `IP`, `PROCESS`, `COMMAND`, `FILE`, `SESSION`), temporal event windows, correlated alerts, attack steps, and MITRE mappings.
* **Roles Supported:** `PRIMARY`, `SUPPORTING`, `CONTEXTUAL`, `CORROBORATING`, `CONTRADICTING`, `TEMPORAL`, `ENTITY_LINK`.
* **Audit Finding:** Bundle structure is deterministic, immutable, and provides complete foundation for M5.4 evidence workbench.

---

### 5. Claims and Hypotheses
* **Current Structure:**
  * `AIClaim` in `apps/engine/src/logintel/ai/domain/response.py` enforces tripartite epistemic statuses: `OBSERVED`, `INFERRED`, `UNKNOWN`.
  * `Hypothesis` in `apps/engine/src/logintel/ai/domain/response.py` represents AI-proposed hypotheses with `HIGH`, `MEDIUM`, `LOW` confidence ratings and explicit unknowns.
* **M5.4 Requirement:** Analyst-owned hypothesis lifecycle:
  ```text
  OPEN → SUPPORTED → WEAKENED → UNRESOLVED → REJECTED
  ```
  Hypotheses must explicitly link supporting evidence, contradicting evidence, evidence gaps, and analyst assessments. AI proposes; analyst decides.
* **Audit Finding:** Pristine foundation exists in M5.3; M5.4 will provide the full analyst hypothesis workflow and status management.

---

### 6. Query Proposals
* **Current Structure:** `QueryProposal` (`apps/engine/src/logintel/ai/domain/intelligence.py`) models structured threat-hunting proposals. `ai_service.preview_query_proposal` executes safe read-only parameterized previews against canonical events (`limit <= 500`). Direct raw SQL execution by AI is completely blocked.
* **M5.4 Requirement:** Complete analyst approval and execution workflow:
  ```text
  AI proposes query → Structured preview → Analyst approves → Deterministic execution → Evidence candidates
  ```
* **Audit Finding:** Preview endpoint exists (`POST /ai/investigations/{id}/query/preview`). M5.4 will add approved query execution (`POST /ai/investigations/{id}/query/execute`) returning results as evidence candidates for the workbench.

---

### 7. AI Response Schema
* **Current Structure:** `AIInvestigationResponse` (`apps/engine/src/logintel/ai/domain/response.py`) defines structured outputs with strict separation between narrative markdown, claims, citations, hypotheses, query proposals, conflicts, and gaps.
* **Audit Finding:** Schema is validated via Pydantic v2 and enforced by `ResponseParser`.

---

### 8. Citation Model
* **Current Structure:** `CitationManifest` (`apps/engine/src/logintel/ai/domain/citation.py`) records all valid citation tags in context. `ResponseParser` rejects any tag not in the manifest with `InvalidCitation` or `CrossInvestigationCitation`.
* **Audit Finding:** Citation enforcement is mathematically complete and tested by 20 security tests.

---

### 9. Analyst Notes
* **Current Structure:** `investigation_notes` and `investigation_notes_audit` tables (Migration 5). Provides CRUD operations, soft-delete tombstones, and immutable audit logging.
* **M5.4 Requirement:** Strict separation:
  ```text
  ANALYST NOTE ≠ AI-GENERATED DRAFT ≠ AUTHORITATIVE EVIDENCE
  ```
* **Audit Finding:** AI may draft note content, but notes must only be persisted via explicit analyst confirmation through `add_note`.
