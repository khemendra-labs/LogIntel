## 1. EXECUTIVE SUMMARY

Milestone 5.5 resolves the primary operational limitation intentionally retained in Milestone 5.4: investigation workspaces were session-scoped and ephemeral, disappearing upon engine process termination. 

M5.5 establishes **controlled investigation continuity and analyst case handoff** through a dedicated persistent investigation repository (`cases.db`) strictly decoupled from the protected forensic SQLite database (`logintel.db`). Under this architectural model:
1. **Forensic Database Preservation:** The authoritative forensic SQLite tables (`events`, `alerts`, `detections`, `incidents`, `incident_entities`, `incident_relationships`, `mitre_tactics`, `investigation_notes`, `investigation_notes_audit`) remain 100% immutable and unmutated across all 141,069 events and 141,913 total rows (`added=0, removed=0, changed=0`).
2. **Migration Invariance:** No Migration 6 is introduced to `logintel.db`. `logintel.db` remains strictly at 5 canonical schema migrations, preserving compatibility with all previous milestone verification contracts.
3. **Dedicated Case Storage:** Investigation cases, hypotheses, evidence references, governed query execution records, report draft versions, and audit logs are persisted in a dedicated SQLite database (`cases.db`) with foreign key constraints and ACID transaction semantics.
4. **Governed Evidence References:** Cases store only pointers (`CaseEvidenceReference`) to authoritative evidence. Raw forensic event payloads are never duplicated into mutable case storage. Stale or deleted evidence is explicitly flagged as `MISSING` or `UNRESOLVED` rather than silently removed or fabricated.
5. **Deterministic AI Context Reconstruction:** Cross-case persistent AI memory, chat-history databases, vector databases, and embeddings are strictly forbidden and excluded. Local AI advisory context is reconstructed deterministically from explicit persistent case state on demand.
6. **Case Handoff & Versioning:** Full support for governed state transitions (`OPEN` → `ACTIVE` → `PAUSED` / `READY_FOR_REVIEW` → `CLOSED` → `ARCHIVED`), multi-version report drafting with diff comparison, analyst ownership handoff with transfer notes, and an immutable audit log.
7. **Verification Rigor:** Verified via 20 dedicated security tests (`M55-SEC-001` through `M55-SEC-020`), 10 functional persistence tests, 410 full engine regression tests, 33 frontend vitest tests, TypeScript production build, and full database content-hash reconciliation.

## 5. PERSISTENT INVESTIGATION MODEL

The persistent case model is implemented in `apps/engine/src/logintel/ai/domain/case.py` and stored via `apps/engine/src/logintel/storage/case_repo.py`.

### Schema in `cases.db`:
```sql
CREATE TABLE IF NOT EXISTS investigation_cases (
    case_id INTEGER PRIMARY KEY,
    incident_id INTEGER NOT NULL UNIQUE,
    title TEXT NOT NULL,
    description TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    created_by TEXT NOT NULL,
    owner TEXT NOT NULL,
    status TEXT NOT NULL CHECK(status IN ('OPEN','ACTIVE','PAUSED','READY_FOR_REVIEW','CLOSED','ARCHIVED')),
    version INTEGER NOT NULL DEFAULT 1,
    scope_json TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS case_hypotheses (
    hypothesis_id TEXT PRIMARY KEY,
    case_id INTEGER NOT NULL REFERENCES investigation_cases(case_id) ON DELETE CASCADE,
    statement TEXT NOT NULL,
    status TEXT NOT NULL,
    supporting_evidence_tags_json TEXT NOT NULL,
    contradicting_evidence_tags_json TEXT NOT NULL,
    evidence_gaps_json TEXT NOT NULL,
    analyst_assessment TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    created_by TEXT NOT NULL,
    version INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE IF NOT EXISTS case_evidence_references (
    reference_id TEXT PRIMARY KEY,
    case_id INTEGER NOT NULL REFERENCES investigation_cases(case_id) ON DELETE CASCADE,
    source_type TEXT NOT NULL,
    source_id TEXT NOT NULL,
    role TEXT NOT NULL,
    epistemic_status TEXT NOT NULL,
    citation_tag TEXT NOT NULL,
    analyst_annotation TEXT,
    created_at TEXT NOT NULL,
    UNIQUE(case_id, source_type, source_id)
);

CREATE TABLE IF NOT EXISTS case_query_history (
    query_id TEXT PRIMARY KEY,
    case_id INTEGER NOT NULL REFERENCES investigation_cases(case_id) ON DELETE CASCADE,
    proposal_id TEXT,
    query_template_id TEXT NOT NULL,
    parameters_json TEXT NOT NULL,
    rationale TEXT,
    executed_by TEXT NOT NULL,
    executed_at TEXT NOT NULL,
    result_count INTEGER NOT NULL,
    execution_status TEXT NOT NULL,
    evidence_candidates_count INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS case_reports (
    report_id TEXT NOT NULL,
    case_id INTEGER NOT NULL REFERENCES investigation_cases(case_id) ON DELETE CASCADE,
    version INTEGER NOT NULL,
    title TEXT NOT NULL,
    origin TEXT NOT NULL,
    generated_by TEXT NOT NULL,
    model_name TEXT,
    model_digest TEXT,
    executive_summary TEXT NOT NULL,
    facts_json TEXT NOT NULL,
    inferences_json TEXT NOT NULL,
    hypotheses_json TEXT NOT NULL,
    unknowns_json TEXT NOT NULL,
    recommendations_json TEXT NOT NULL,
    citation_manifest_json TEXT NOT NULL,
    is_final INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL,
    created_by TEXT NOT NULL,
    PRIMARY KEY(case_id, report_id, version)
);

CREATE TABLE IF NOT EXISTS case_audit_log (
    audit_id INTEGER PRIMARY KEY AUTOINCREMENT,
    case_id INTEGER NOT NULL REFERENCES investigation_cases(case_id) ON DELETE CASCADE,
    timestamp TEXT NOT NULL,
    actor TEXT NOT NULL,
    action TEXT NOT NULL,
    previous_value TEXT,
    new_value TEXT,
    reason TEXT
);
```

## 6. CASE LIFECYCLE & GOVERNED TRANSITIONS

State transitions follow a strict deterministic finite state machine implemented in `ALLOWED_CASE_TRANSITIONS`:

```text
           +-----------------------------+
           |            OPEN             |
           +-----------------------------+
                          │
                          │ (Start Investigation)
                          ▼
           +-----------------------------+
     ┌────>│           ACTIVE            │<────┐
     │     +-----------------------------+     │
     │        │                       │        │
     │        │ (Pause)               │ (Review)
     │        ▼                       ▼        │
(Resume)  +--------+             +--------------+
     │    | PAUSED |             | READY_FOR_   |
     └────+--------+             |    REVIEW    |
                                 +--------------+
                                        │
                                        │ (Approve & Close)
                                        ▼
                                 +--------------+
                         ┌──────>│    CLOSED    │
                         │       +--------------+
                     (Reopen)           │
                         │              │ (Archive)
                         │              ▼
                         │       +--------------+
                         └───────|   ARCHIVED   |
                                 +--------------+
```

### Valid Transition Matrix
| Source State | Target State | Governed Action / Validation |
| :--- | :--- | :--- |
| `OPEN` | `ACTIVE` | Initial analyst activation |
| `ACTIVE` | `PAUSED` | Investigation temporarily halted |
| `ACTIVE` | `READY_FOR_REVIEW` | Findings drafted, ready for peer review |
| `PAUSED` | `ACTIVE` | Investigation resumed by analyst |
| `READY_FOR_REVIEW`| `ACTIVE` | Review returned for further evidence |
| `READY_FOR_REVIEW`| `CLOSED` | Formal case closure |
| `CLOSED` | `ACTIVE` | Explicit analyst reopening |
| `CLOSED` | `ARCHIVED` | Long-term archival preservation |
| `ARCHIVED` | `ACTIVE` | Explicit administrative unarchival |

Any invalid transition (e.g. `OPEN` → `CLOSED` or `PAUSED` → `ARCHIVED`) is strictly rejected with a HTTP 400 Bad Request.

## 7. EVIDENCE REFERENCE MODEL & STALE DETECTION

Rather than cloning raw event payloads into mutable case tables, LogIntel persists only evidence pointers:
- `source_type`: `event`, `alert`, `detection`, `entity`
- `source_id`: e.g. `evt-101`, `alert-301`
- `citation_tag`: e.g. `[event:evt-101]`
- `epistemic_status`: `OBSERVED`, `INFERRED`, or `HYPOTHETICAL`
- `analyst_annotation`: Analyst commentary explaining relevance

### Dynamic Resolution & Stale Detection
When a case is loaded, `CaseRepository.resolve_evidence_references()` cross-references every pointer against `logintel.db`:
- **`AVAILABLE`**: The authoritative row exists in the forensic database and is resolved into `resolved_record`.
- **`MISSING`**: The referenced record cannot be located in the authoritative database (e.g. pruned or archived).
- **`UNRESOLVED`**: The pointer format or source table is unknown.

**Hard Rule:** Stale evidence references are **never silently deleted or fabricated**. The UI and AI context explicitly flag missing evidence to maintain forensic honesty.

## 8. HYPOTHESIS PERSISTENCE

Analyst hypotheses are persisted across engine restarts with versioning and audit history:
- Statuses: `OPEN`, `SUPPORTED`, `WEAKENED`, `UNRESOLVED`, `REJECTED`
- Supporting citation tags and contradicting citation tags

- Analyst assessment notes

**Authority Boundary:** Local AI may propose candidate hypotheses, but only the authenticated human operator can commit, transition status, or finalize assessments.

- Parameterized execution only (no arbitrary SQL execution)

- Candidates discovered via queries can be selectively promoted to case evidence references.

## 10. AI CONTEXT RECONSTRUCTION & ZERO CROSS-CASE MEMORY

M5.5 enforces strict context reconstruction boundaries:
1. **Zero Persistent AI Memory:** No chatbot conversational memory or embedding database is maintained.
2. **Deterministic Re-assembly:** When an AI operation is requested, `CaseService.reconstruct_ai_context(case_id)` builds context solely from:
   - Current case metadata and status
   - Bound investigation scope
   - Resolved authoritative evidence references
   - Persisted hypotheses and evidence gaps
   - Approved query execution records
   - Latest report draft version
3. **Isolation:** Context from Case A is completely inaccessible to Case B.

## 11. AI CONTENT PROVENANCE & LABELING

All persisted report versions and findings maintain explicit content origin labels:
- `ANALYST_AUTHORED`: Authored directly by the human security analyst.
- `AI_GENERATED`: Advisory content produced by the local AI engine.
- `SYSTEM_GENERATED`: Telemetry or rule-engine produced content.

When `origin == AI_GENERATED`, the record stores:
- `model_name`: e.g. `qwen2.5:0.5b`
- `model_digest`: Provider digest or runtime identifier
- `citation_manifest`: Complete list of evidence tags cited in the generation

Analyst edits to report drafts create new versions or revisions, preventing silent AI overwrites.

## 12. REPORT DRAFT CONTINUITY & VERSION COMPARISON

Reports support full multi-version lifecycle:
- Generating a report creates an incremented version (v1, v2, v3...)
- Each version retains independent executive summaries, facts, inferences, and recommendations
- `CaseService.compare_report_versions(case_id, report_id, v1, v2)` provides structural and text diffing:
  - Added / removed forensic facts
  - Unified diff of executive summary lines
  - Added / removed recommendations

## 13. CASE HANDOFF

Shift transfer and peer handoff are supported via `transfer_case`:
- Updates `case.owner`
- Increments `case.version`
- Records an immutable `CASE_HANDOFF` audit log entry with `previous_owner`, `new_owner`, and analyst handoff notes
- Single-tenant local IPC security model: Local operator acts on behalf of designated analyst identities without introducing complex multi-tenant enterprise RBAC.

## 23. KNOWN DOCUMENTED LIMITATIONS

1. **Persistent Case State vs. Persistent AI Memory:** M5.5 persists analyst investigation state (scope, hypotheses, evidence references, query history, reports, and audit trail). It does **NOT** provide unrestricted chatbot memory or conversational embedding recall across cases.
2. **Single-Tenant Local Authentication:** Authentication utilizes a single-tenant local IPC bearer token. While case records track `owner` and `actor` metadata for handoff auditing, this does not constitute multi-tenant enterprise RBAC.
3. **Local AI Model Capabilities:** Explanations and drafted sections depend on the reasoning capability of the locally hosted Ollama model (`qwen2.5:0.5b`). While citation grounding is strictly enforced, analysts remain the final authoritative decision-makers.
4. **Stale Evidence References:** If authoritative evidence is removed from the forensic database, references are marked `MISSING` rather than resolved. The system does not attempt to reconstruct missing raw logs.
