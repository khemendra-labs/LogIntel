6. **Structured Investigation Summary & Report Drafting:** Deterministic generation of structured investigation summaries and evidence-grounded report drafts separating facts, inferences, hypotheses, and unknowns, with one-click promotion into authoritative analyst notes.
7. **Zero Authoritative Mutation:** Database reconciliation confirms `added = 0, removed = 0, changed = 0` across all 8 core tables (141,069 events; 141,913 total records) and Migration 6 remains strictly absent.

## 5. INVESTIGATION WORKSPACE & LIFECYCLE

The investigation workspace provides a deterministic state machine:

```text
                  ┌───────────────┐
                  │     OPEN      │
                  └───────┬───────┘
                          │
                          ▼
                  ┌───────────────┐
           ┌─────►│    ACTIVE     │◄─────┐
           │      └───┬───┬───┬───┘      │
           │          │   │   │          │
           │   ┌──────┘   │   └──────┐   │
           │   ▼          ▼          ▼   │
       ┌───────┴┐   ┌─────────┐   ┌──┴───┴┐
       │ PAUSED │   │ CLOSED  │   │ READY │
       └────────┘   └─────────┘   │  FOR  │
                                  │REVIEW │
                                  └───────┘
```

* **Validated State Transitions (`ALLOWED_INVESTIGATION_TRANSITIONS`):**
  * `OPEN` → `ACTIVE`, `CLOSED`
  * `ACTIVE` → `PAUSED`, `READY_FOR_REVIEW`, `CLOSED`
  * `PAUSED` → `ACTIVE`, `CLOSED`
  * `READY_FOR_REVIEW` → `ACTIVE`, `CLOSED`
  * `CLOSED` → Terminal state (no further transitions permitted)
* **Audit Trail:** Every state change records `timestamp`, `actor`, `previous_state`, `new_state`, and `reason` in `state_history`.
* **Analyst Governance:** State transitions are restricted to authenticated analyst requests; AI completion cannot alter the investigation state.

## 6. INVESTIGATION SCOPE

Every investigation workspace maintains an explicit, reproducible scope:
* `investigation_id` (integer)
* `time_start` & `time_end` (ISO 8601 UTC timestamps)
* `subject_type` (`incident`) & `subject_id`
* `selected_entity_ids` (e.g., `["srv-prod-01", "user:deployer"]`)
* `selected_alert_ids`, `selected_detection_ids`, `selected_event_ids`

When scope is updated by an analyst, all subsequently generated summaries, evidence bundles, and reports resolve strictly against the bounded scope. No event or detection data is duplicated in the scope model.

## 7. EVIDENCE WORKBENCH

The Evidence Workbench organizes evidence from M5.3 with explicit provenance and roles:
* **Roles Supported:** `PRIMARY`, `SUPPORTING`, `CONTEXTUAL`, `CORROBORATING`, `CONTRADICTING`, `TEMPORAL`, `ENTITY_LINK`.
* **Epistemic Qualification:** Every item is marked with its epistemic category:
  * `OBSERVED`: Authoritative records directly present in the forensic database.
  * `INFERRED`: Derived analytical linkages or query candidate results.
  * `UNKNOWN`: Telemetry gaps or unestablished relationships.
* **Evidence Provenance:** Every evidence item tracks `source_table`, `source_id`, `citation_tag`, `timestamp`, and `role`.
* **Candidate Staging:** Results from approved threat hunt queries enter as `evidence_candidates` without polluting authoritative detection tables.

## 8. HYPOTHESIS WORKFLOW

Hypotheses are modeled as first-class, analyst-owned constructs (`AnalystHypothesis`):
* **States:** `OPEN`, `SUPPORTED`, `WEAKENED`, `UNRESOLVED`, `REJECTED`.
* **Structure:**
  * `hypothesis_id`: Unique identifier (e.g., `hyp-38-1`).
  * `statement`: Analyst formulation of potential threat activity.
  * `supporting_evidence`: List of verified citation tags (`[event:...]`, `[alert:...]`).
  * `contradicting_evidence`: List of contradicting citation tags.
  * `evidence_gaps`: Identified missing telemetry or unanswered questions.
  * `analyst_assessment`: Freeform analytical reasoning.
* **AI Invariant:** AI is permitted only to propose hypothesis wording or suggest supporting/contradicting tags; the analyst retains sole authority over creation, status transitions, and final assessments.

---

## 9. EXPLAINABILITY & PROVENANCE LAYER

Every AI-assisted claim is explainable down to the underlying database records:
* **ClaimTrace Contract:** Resolves citation tags to source tables (`events`, `alerts`, `detections`, `incident_entities`, `mitre_tactics`) and returns the exact database row and timestamp.
* **Epistemic Labeling:** The UI and backend enforce explicit separation:
  * `OBSERVED`: Verified SSH authentication failure, command execution, or network packet.
  * `INFERRED`: Probable sequence correlation or lateral movement candidate.
  * `UNKNOWN`: Unrecorded telemetry or out-of-scope activity.
  * `HYPOTHESIS`: Working analytical proposition pending evidence.

---

## 10. QUERY PROPOSAL & GOVERNED EXECUTION WORKFLOW

Threat-hunting queries proposed by AI undergo strict governance:
1. **Catalog Validation:** Proposals must match predefined, allowlisted query templates (`query_failed_logins_by_user`, `query_process_lineage_by_parent`, etc.).
2. **Parameter Sanitization:** Parameters are strictly validated and parameterized; raw SQL cannot be submitted by model completions.
3. **Analyst Approval:** Query execution requires explicit POST request to `/query/execute` by an authenticated analyst.
4. **Deterministic Execution:** The engine executes parameterized queries and stages matching events into `evidence_candidates` in the investigation workspace without mutating authoritative detection tables.

## 23. LIMITATIONS & KNOWN NON-GOALS

1. **In-Memory Workspace Lifecycle:** Investigation workspace lifecycle states and hypothesis records reside in memory per engine process session to guarantee zero modification to authoritative SQLite tables and avoid unapproved schema migrations.
2. **Cataloged Threat Hunt Queries:** Query proposals support allowlisted query templates only (`query_failed_logins_by_user`, `query_process_lineage_by_parent`, `query_network_connections_by_ip`, etc.). Arbitrary SQL generation is strictly prohibited.
3. **Application-Level Injection Containment:** Prompt-injection mitigation is achieved through strict JSON schema parsing, boundary tagging, and citation verification; the local LLM itself is not inherently immune to adversarial prompt text.
4. **Advisory Role:** AI cannot transition investigation states, resolve alerts, or alter authoritative evidence.
