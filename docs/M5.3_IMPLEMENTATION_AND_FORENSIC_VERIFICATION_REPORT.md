## 6. EVIDENCE BUNDLE

The evidence bundle is modeled in `apps/engine/src/logintel/ai/domain/bundle.py`:

```python
class EvidenceItem(BaseModel):
    evidence_id: str
    evidence_type: EvidenceType
    source_id: str
    source_table: str
    timestamp: str
    relevance_score: float = Field(default=1.0, ge=0.0, le=1.0)
    role: EvidenceRole
    citation_tag: str
    summary: str
    metadata: Dict[str, Any] = Field(default_factory=dict)
```

Bundle Invariants:
1. Every evidence item retains unambiguous provenance (`source_table`, `source_id`, `evidence_id`).
2. Citation tags follow strict bracket notation: `[event:<id>]`, `[alert:<id>]`, `[entity:<key>]`, `[step:<num>]`, `[mitre:<id>]`.
3. Timestamp serialization is strictly normalized to ISO-8601 strings.
4. Duplicate entries are eliminated via `seen_evidence_ids: Set[Tuple[str, str]]`.

## 7. ENTITY-CENTRIC RETRIEVAL

The retriever explicitly supports all seven M3/M4 entity types:
* `HOST`: Host telemetry, host-based alerts, primary host mappings.
* `USER`: Identity context, authentication outcomes, sudo/privilege events.
* `IP`: Source and destination IP activity, external communication telemetry.
* `PROCESS`: Executable processes, parent-child process relationships.
* `COMMAND`: Full command lines, invocation arguments, execution events.
* `FILE`: File paths accessed, modified, or quarantined.
* `SESSION`: Authentication sessions, SSH sessions, terminal session linkages.

When `target_entity` is provided to `retrieve_bundle(target_entity=...)`:
* Items matching the target entity receive elevated relevance scores (0.95 vs 0.70).
* Irrelevant non-matching entities are deprioritized or pruned to preserve context budget.
* Verification: Verified in unit test `test_evidence_retriever_all_seven_entity_types`.

## 8. TIMELINE RETRIEVAL

Timeline retrieval operates in two distinct modes:
1. **Investigation Timeline Retrieval (`retrieve_timeline_evidence`):** Extracts all chronological events, alerts, and attack-path steps within an incident, sorted strictly by `(timestamp ASC, evidence_id ASC)`.
2. **Surrounding Events Retrieval (`retrieve_surrounding_events`):** Given a focal `event_id` and a window (e.g. 1800 seconds), returns events categorized into:
   - `before`: Preceding events on the same host within the window.
   - `target`: The exact focal event.
   - `after`: Subsequent events on the same host within the window.

Critical distinction: Temporal proximity is reported as an `OBSERVED SEQUENCE`, never converted automatically into an inferred causal link.

## 9. EVIDENCE CORROBORATION

The bundle engine identifies corroborating telemetry when independent evidence records converge on the same entity or attack step.
* For example, multiple consecutive authentication failures from an IP followed by a successful login are grouped as corroborating telemetry.
* Epistemic rule: Corroboration increases confidence in an analytical hypothesis, but does **not** convert the hypothesis into an observed forensic fact.
* Inferred claims must still retain `INFERRED` status with an explicit rationale.

---

## 10. CONFLICT DETECTION

Conflicting or contradictory forensic evidence is audited deterministically in `retriever._detect_conflicts`:
* **Temporal Ordering Anomaly:** E.g., successful login occurring after an account termination event or preceding repeated failures.
* **Missing Process Telemetry:** A privileged command execution event without corresponding auditd/process telemetry.
* **Conflicting Host/Source States:** Telemetry reporting mutually exclusive network or service outcomes.

Model Structure:
```python
class EvidenceConflict(BaseModel):
    conflict_id: str
    conflict_type: str
    evidence_tag_a: str
    evidence_tag_b: str
    description: str
    severity: str = "MEDIUM"
```

The system never attempts to resolve conflicts autonomously; contradictions are surfaced transparently to the human analyst.

## 11. EVIDENCE GAPS

Visibility gaps are explicitly audited and reported via `EvidenceGap`:
* Checks for absence of process execution telemetry (`auditd`).
* Checks for absence of network connection flow telemetry.
* Audits omitted evidence types from the investigation bundle.

Epistemic Invariant:
> **Absence of evidence is never converted into evidence of absence.**
Missing audit logs simply indicate lack of visibility; the AI is strictly barred from asserting that an action did not occur due to missing logs.

## 12. CLAIM/EVIDENCE MODEL

In-memory claims are structured according to the tripartite epistemic model:
```text
CLAIM
├── OBSERVED (Directly supported by cited forensic tags in context)
├── INFERRED (Analytical deduction requiring supporting tags + explicit rationale)
└── UNKNOWN (Explicit disclosure of visibility gap; strictly zero evidence tags allowed)
```

Validation Rules in `ResponseParser`:
* An `OBSERVED` claim with no evidence references is rejected with `InvalidEpistemicClaim`.
* An `INFERRED` claim without a rationale is rejected with `InvalidEpistemicClaim`.
* An `UNKNOWN` claim that attaches evidence citations is rejected with `InvalidEpistemicClaim`.
* Any attempt to cite a non-existent or cross-incident evidence tag raises `InvalidCitation` or `CrossInvestigationCitation`.

To maximize relevance under constrained token budgets, M5.3 implements prioritized context selection:
1. **Tier 1:** Incident header & investigation dossier.

4. **Tier 4:** Attack path progression steps.

7. **Tier 7:** Contradicting events and evidence gaps.

Every selected item includes an explainable `relevance_score` between 0.0 and 1.0.

## 16. HYPOTHESIS HANDLING

Hypotheses represent analytical possibilities, not observed facts:
```python
class Hypothesis(BaseModel):
    hypothesis_id: str
    statement: str
    confidence: HypothesisConfidence  # HIGH, MEDIUM, LOW
    supporting_evidence: List[Any]
    contradicting_evidence: List[Any]
    rationale: str
    unknowns: List[str]
    is_hypothesis: bool = True
```

Constraints:
* Confidence is restricted to `HIGH`, `MEDIUM`, or `LOW` (qualitative epistemic rating, never statistical certainty).
* Hypotheses cannot automatically create alerts, detections, or incidents.
* Hypotheses must list known ambiguities in `unknowns`.

## 28. KNOWN LIMITATIONS

1. **Context Window Constraint:** The 2,048-token context window of lightweight local models (`qwen2.5:0.5b`) restricts the number of supporting telemetry events that can be concurrently submitted in a single prompt. Adaptive budgeting mitigates this by prioritizing primary detection events and omitting lower-priority contextual records with transparent audit logging.
2. **Deterministic Question Classifier:** The intent classifier uses deterministic regex heuristics. While fast (<1.2ms) and predictable, highly informal or colloquial phrasing may fall back to `InvestigationIntent.GENERAL`.
3. **No Direct Model Threat-Hunting Execution:** By strict security design, suggested queries cannot be directly executed by the model; analyst approval and preview trigger is required.
