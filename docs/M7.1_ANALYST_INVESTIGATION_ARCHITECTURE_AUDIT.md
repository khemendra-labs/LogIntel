## 1. Executive Summary

Milestone M7.1 conducts a comprehensive, read-only architectural, product-boundary, and implementation-readiness audit of the LogIntel platform following the formal closure and certification of Milestones M1 through M6.

The purpose of this audit is to prevent redundant re-implementation of capabilities established across M1–M6, rigorously assess the state of analyst investigation operations, define the governing product and security boundaries, and chart a concrete implementation roadmap for M7.

### Primary Audit Findings:
1. **Substantial Primitives Already Exist (M5/M6):** Contrary to assumptions that M7 requires building an entire investigation system from scratch, the LogIntel repository already contains extensive investigation infrastructure:
   - Dedicated, ACID-compliant analyst case database (`cases.db`) with append-only triggers and strict POSIX permissions (`0600`/`0700`).
   - Deterministic case assessment engine with categorical evidence sufficiency, closure readiness, structured findings, and competing hypotheses.
   - Comprehensive API surface with **144 registered routes** (including 70+ dedicated to cases, investigations, graphs, temporal reconstructions, and assessments).
   - Rich frontend components in `apps/desktop/src/features/` including `IncidentWorkspaceModal`, `InvestigationAssessmentExplorer`, `InvestigationTemporalExplorer`, `InvestigationGraphExplorer`, and `InvestigationCorrelationExplorer`.
2. **Key Architectural Problem Is Fragmentation, Not Missing Telemetry:** The existing capabilities were developed across sequential milestones (M4 notes, M5.4–M5.11 intelligence/assessments, M6.8–M6.9 host graphs). They currently suffer from UI fragmentation—many advanced tools are buried inside nested subtabs of an "AI" panel inside an `IncidentWorkspaceModal` rather than presented as a unified, first-class analyst workspace.
3. **Forensic Database Boundary Is Pristine:** The authoritative forensic telemetry database (`logintel.db`) remains completely separated from the analyst case database (`cases.db`). Database integrity checks (`PRAGMA integrity_check`) return `ok` with zero foreign-key violations on both databases.
4. **No Schema Migration Required:** `logintel.db` remains frozen at exactly 5 canonical migrations (`len(MIGRATIONS) == 5`). Proposed M7 capabilities can be entirely accommodated using the existing schema of `cases.db` and in-memory projection models. **Migration 7 is NOT required and is explicitly rejected.**
5. **Security & AI Boundaries Are Strictly Governed:** Local AI advisory services operate with `is_authoritative = False`, strict context budgeting, prompt-injection containment, and zero database mutation or shell execution paths.

  - `trg_prevent_case_audit_delete`: Aborts any `DELETE` on `case_audit_log`.
  - `trg_prevent_case_delete`: Aborts any `DELETE` on `investigation_cases` (enforces archival instead of physical deletion).
  - `trg_prevent_case_report_update`: Prevents modifying reports marked `is_final = 1`.
  - `trg_prevent_case_report_delete`: Prevents deleting finalized reports.

## 8. Evidence & Provenance Audit

LogIntel strictly enforces the forensic trust hierarchy:

```text
RAW EVENT (Syslog, Journald, Auditd, /proc)
    ↓
CANONICAL EVENT (Structured, Normalized ISO-8601 UTC, Ingestion Hash)
    ↓
DETECTION EVIDENCE (Forensic binding in detection_evidence)
    ↓
CASE EVIDENCE REFERENCE (Pointer in case_evidence_references, Stale-Check)
    ↓
STRUCTURED FINDING (Epistemic State: OBSERVED / INFERRED / UNKNOWN)
    ↓
ANALYST REVIEW (Review State: UNREVIEWED / ACCEPTED / REJECTED / DISPUTED)
    ↓
PROVENANCE MANIFEST (SHA-256 Merkle root of all contributing records)
```

### Stale Evidence Resolution
`CaseRepository.get_case_evidence_references()` performs dynamic resolution checks against `logintel.db`. If a referenced event exists in the canonical database, `resolution_status` evaluates to `AVAILABLE`. If an event was pruned or missing, it resolves to `MISSING`, preventing silent corruption of case facts.

### Epistemic Separation
Epistemic classification (`OBSERVED`, `INFERRED`, `UNKNOWN`) is strictly decoupled from analyst review state (`UNREVIEWED`, `ACCEPTED`, `REJECTED`, `DISPUTED`). An analyst accepting an inference does **not** convert it to `OBSERVED`; it remains `INFERRED (ACCEPTED)`.

## 9. Security Boundary Audit

The audit rigorously evaluated all potential vulnerability classes across the engine and frontend:

1. **SQL Injection:** Zero dynamic SQL string concatenation. All SQL operations across `events_repo`, `incidents_repo`, and `case_repo` utilize strict parameterized queries (`?` parameter binding).
2. **Command Injection & Shell Execution:** Zero usage of `os.system()`, `subprocess.Popen(shell=True)`, or unsanitized shell invocations in the runtime path. All telemetry collection utilizes direct POSIX file operations, standard library socket APIs, and structured `/proc` parsing.
3. **Case Isolation & Cross-Case Leakage:** All case operations require an explicit integer `case_id`. Foreign keys in `cases.db` enforce relational integrity with `ON DELETE CASCADE`. Queries strictly filter on `WHERE case_id = ?`.
4. **File Permissions & Storage Security:** `CaseRepository` enforces POSIX permissions `0600` on `cases.db` and WAL files, and `0700` on the parent directory on every connection instantiation.
5. **Path Traversal:** No user-supplied or AI-supplied paths are written to disk. Reports and exports return streaming text responses or write to sandboxed application directories.
6. **Authentication & Authorization:** All API endpoints (except `/api/v1/handshake`) enforce Bearer token verification via `verify_engine_token`. The token is dynamically generated on engine startup and written to a protected local IPC token file.

## 10. AI Boundary & Containment Audit

Local AI investigation intelligence (Ollama) is governed by strict architectural guardrails:

1. **Strictly Read-Only & Advisory:** All AI responses carry `is_authoritative = False`. AI suggestions cannot mutate authoritative detections, alter case state, modify evidence references, or close incidents.
2. **Zero Direct Execution Privileges:** The AI engine has no capability to execute arbitrary SQL, shell commands, network requests, or remediation actions.
3. **Application-Level Prompt Injection Containment:** Implemented in `AssessmentEngine._sanitize_string()` and context serializers:
   - Control characters (`\x00`–`\x1F`) are stripped.
   - Text is clamped to bounded token lengths.
   - Evidence records are formatted as structured, typed JSON schemas rather than unstructured natural text.
4. **Evidence Grounding & Citations:** AI explanations are rejected or flagged if they make claims without citing specific evidence tags present in the structured context window.
5. **Local-Only Operational Boundary:** All AI processing is bound to local Ollama instances (`http://127.0.0.1:11434`). Zero cloud telemetry upload or external vector database connections exist.

## 18. Database Migration Decision

### **DECISION: MIGRATION 7 IS NOT REQUIRED AND IS EXPLICITLY REJECTED.**

#### Technical Rationale:
1. **Forensic Database Stability:** `logintel.db` houses authoritative, append-only forensic telemetry. Its schema migrations are frozen at 5. Any migration to `logintel.db` would violate the forensic boundary established in M1–M6.
2. **Sufficient Schema in `cases.db`:** The dedicated analyst database (`cases.db`) already contains 10 comprehensive tables designed in M5.5 and M5.11:
   - `investigation_cases`, `case_hypotheses`, `case_evidence_references`, `case_query_history`, `case_reports`, `case_audit_log`, `case_finding_reviews`, `case_transition_reviews`, `case_assessments`, `case_investigation_questions`.
3. **Extensibility via Existing Columns:**
   - Logical Evidence Collections (M7-13) can be represented using `case_evidence_references.citation_tag`, `role`, or metadata JSON without altering table schemas.
   - Case Comparison (M7-14) is a deterministic in-memory computation across existing case records.
   - Interactive Replay (M7-11) is a frontend state machine over existing temporal transitions.
4. **Zero Persistent Schema Additions Justified:** Introducing Migration 7 would increase maintenance overhead with zero technical benefit.
