## 1. Executive Summary

Milestone M7.5 introduces an analyst-oriented threat hunting and governed investigative query operational layer to the LogIntel forensic investigation platform. M7.5 strictly enforces the foundational epistemological and security invariant:

$$\text{THREAT HUNTING} \neq \text{DETECTION}$$

A threat hunt poses an analyst-directed question: *"Show me candidate evidence matching this investigative inquiry."* In contrast, authoritative detection represents an algorithmic, deterministic match against an authoritative, rule-bound detection engine. Consequently, hunt execution:
- Never automatically generates authoritative detections or alerts.
- Never automatically classifies events or entities as malicious.
- Never modifies the epistemic status of raw evidence or converts unobserved events into absence of events.
- Never accepts hypotheses, closes cases, or assigns numerical probabilities or confidence scores.
- Never executes arbitrary SQL, shell scripts, subprocesses, or unconstrained dynamic code.

The M7.5 operational pipeline implements a multi-stage governed lifecycle:
$$\text{Question} \longrightarrow \text{Hunt Intent} \longrightarrow \text{Structured Query Proposal} \longrightarrow \text{Deterministic Preview} \longrightarrow \text{Analyst Approval Gate} \longrightarrow \text{Bounded Execution} \longrightarrow \text{Evidence Lineage Results} \longrightarrow \text{Pivots / Findings / Hypotheses / Collections}$$

All 20 dedicated security controls (M75-SEC-001 through M75-SEC-020) achieved **20/20 PASS**. Deterministic execution across $N=10$ iterations demonstrated byte-identical query previews, execution item sequences, and Blake2b export fingerprints. Performance benchmarking on local hardware demonstrated sub-10ms governed execution and sub-2ms query validation latencies. Both authoritative databases (`logintel.db` and `cases.db`) passed `PRAGMA integrity_check` and `PRAGMA foreign_key_check` with zero schema migrations added (schema migration count frozen at 5).

## 5. Hunt Model

The M7.5 Hunt Model represents queries via controlled Abstract Syntax Trees (AST) using categorical intents:
- `PROCESS_EXECUTION`
- `AUTHENTICATION_ACTIVITY`
- `PRIVILEGE_ESCALATION`
- `NETWORK_CONNECTION`
- `FILE_ACTIVITY`
- `PERSISTENCE`
- `SYSTEMD_SERVICE_ACTIVITY`
- `CONTAINER_ACTIVITY`
- `USER_SESSION`
- `CROSS_HOST_ACTIVITY`
- `IOC_LOOKUP`
- `ENTITY_ACTIVITY`
- `TEMPORAL_SEQUENCE`
- `CORRELATION`

Arbitrary natural language text is treated exclusively as human-readable context (`question`). Execution requires typed, validated fields and allowlisted operators (`equals`, `not_equals`, `contains`, `prefix`, `suffix`, `in`, `not_in`, `exists`, `range`, `before`, `after`, `between`).

## 6. Query Governance & Resource Bounds

To prevent Denial of Service (DoS) and uncontrolled resource consumption, every query is bound by `HuntResourceBounds`:
- **Maximum Result Limit:** Bounded to 1,000 records (default: 100). Exceeding this boundary triggers deterministic truncation with `is_truncated = True`.
- **Maximum Time Window:** 30 days. Attempts to query beyond 30 days are rejected with `RESOURCE_LIMIT_EXCEEDED` / `INVALID_QUERY`.
- **Maximum Query Complexity:** Complexity score calculated from filter counts and join requirements, bounded to $\le 10$.
- **Pagination Boundary:** Maximum offset bounded to 1,000.
- **Maximum Duration:** Execution duration timeout monitored.
- **Deterministic Ordering:** Stable tie-breaking order: `timestamp ASC, source ASC, id ASC`. SQLite implicit row order is never relied upon.

## 8. Case Isolation

Case isolation is enforced at the repository and service layers:
- All hunting endpoints resolve through `case_id`.
- Execution records are stored in `case_query_history` with foreign key binding to `cases.case_id`.
- Cross-case query listing, retrieval, export, or finding conversion attempts across cases fail with deterministic `HTTP 404 Not Found` or `ValueError`.
- Security tests `M75-SEC-004`, `M75-SEC-005`, and `M75-SEC-006` verified zero cross-case leakage across isolated cases `7511` and `7512`.

## 9. Evidence Provenance & Epistemic Boundaries

Every hunt result item returned maintains complete forensic lineage:
- `result_id`: Unique deterministic identifier (`HRES-{source_type}-{source_id}`).
- `source_type`: Originating telemetry layer (`event`, `auditd`, `network`, etc.).
- `source_id`: Authoritative identifier in `logintel.db`.
- `citation_tag`: Human-readable forensic tag (e.g., `EVT-75001`).
- `provenance_hash`: SHA-256 digest of original raw event payload and metadata.
- `epistemic_status`: `OBSERVED`, `INFERRED`, or `UNKNOWN`.

Forensic payloads are never duplicated into new raw storage tables. Results are references to authoritative records.

## 10. AI Boundary & Advisory Invariants

Local AI integration operates under strict containment invariants:
- **Proposal Only:** AI takes natural language input and outputs a `GovernedQueryModel` proposal.
- **Approval Mandatory:** AI output is instantiated in `DRAFT` state. The approval state machine (`DRAFT -> VALIDATED -> READY -> APPROVED -> EXECUTING -> COMPLETED`) prohibits execution without explicit human analyst action (`approved_by: str`).
- **Prompt Injection Containment:** Prompt injection strings inside natural language questions or evidence summaries cannot trigger shell execution, database writes, or automated case status mutations. Verified in `M75-SEC-014` and `M75-SEC-020`.
- **Local-Only:** No external cloud AI APIs, remote vector databases, or telemetry egress are utilized.
