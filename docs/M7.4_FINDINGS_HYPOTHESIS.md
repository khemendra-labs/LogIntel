## 1. Architectural Mission & Core Invariants

Milestone M7.4 delivers the dedicated analyst workbench for constructing, versioning, evaluating, and reviewing findings and hypotheses:

```text
Evidence
    ↓
Evidence Collection
    ↓
Finding
    ↓
Hypothesis
    ↓
Analyst Review
    ↓
Assessment
```

### 1.1 The Forensic Trust Boundary Axiom

```text
OBSERVED EVIDENCE  ≠  ANALYST FINDING  ≠  HYPOTHESIS  ≠  FINAL CONCLUSION
```

1. **Observed Evidence:** Concrete, immutable forensic events and host telemetry recorded by sensors and collectors.
2. **Analyst Finding:** An analyst-authored factual or inferred proposition directly grounded in attached evidence references.
3. **Hypothesis:** A provisional explanatory model under active investigation that accounts for observed evidence, accounts for contradictions, and identifies evidence gaps.
4. **Analyst Review:** An explicit human analyst governance judgment (`UNREVIEWED`, `ACCEPTED`, `REJECTED`, `DISPUTED`).
5. **Final Assessment & Report:** Synthesized investigation conclusions referencing accepted findings and evaluated hypotheses.

Under no circumstances does local AI or automated processing silently promote an inference to an observed fact, nor does creating a hypothesis convert provisional propositions into facts.

### 1.2 Epistemic State vs. Review State Separation

Epistemic status represents the objective knowledge grounding of a finding:
- `OBSERVED`: Directly corroborated by primary forensic telemetry.
- `INFERRED`: Derived via analytical reasoning from observed evidence.
- `UNKNOWN`: Uncorroborated analyst statement or open lead.

Review status represents human analyst governance:
- `UNREVIEWED`: Newly authored or updated finding awaiting review.
- `ACCEPTED`: Analyst concurs with the proposition and grounding.
- `REJECTED`: Analyst determines the proposition is refuted or unsupported.
- `DISPUTED`: Analyst notes conflicting evidence or contradictory interpretations.

**Critical Invariant:** Reviewing a finding as `ACCEPTED` never transforms its epistemic status from `INFERRED` to `OBSERVED`.

### 1.3 Categorical Metrics — Zero Fake Probabilities

To ensure forensic integrity and avoid misleading quantitative pseudo-precision:
- Numerical confidence scores (`confidence = 0.87`), risk percentages (`risk = 74%`), and probabilistic likelihoods are strictly prohibited.
- All hypothesis evaluations use deterministic categorical indicators:
  - `SUPPORTING` evidence counts and tags
  - `CONTRADICTING` evidence counts and tags
  - Explicit categorical `evidence_gaps` (e.g., `AUDIT_RULE_NOT_CONFIGURED`, `TELEMETRY_DROPPED`, `NO_EVENT_OBSERVED`)
  - Explicit categorical status (`OPEN`, `SUPPORTED`, `WEAKENED`, `DISPUTED`, `INCONCLUSIVE`, `REJECTED`)

## 3. Findings & Hypothesis Service Architecture

Implemented in `apps/engine/src/logintel/findings/service.py` (`FindingsWorkbenchService`).

### 3.1 Finding Creation & Evidence Grounding
- An analyst can create a finding directly from evidence references, collections, timeline items, attack graph entities, or investigation questions.
- If a finding is authored without attached evidence references, its epistemic status is enforced as `UNKNOWN` or `INFERRED` with explicit warning, preventing ungrounded assertions from appearing authoritative.

### 3.2 Finding Versioning & Immutability
- Every edit to a finding (`title`, `statement`, `epistemic_status`, `severity`, etc.) archives the previous state into `version_history`.
- Version history preserves `version`, `title`, `statement`, `epistemic_status`, `review_status`, `created_at`, `actor`, and `change_reason`.
- Authoritative audit log entries are generated for every mutation.

### 3.3 Evidence Attachment & Deletion Semantics
- Attaching evidence to a finding references existing case evidence records without copying raw telemetry payloads.
- **Evidence Immutability:** Disassociating evidence from a finding removes only the finding-to-evidence reference; the underlying case evidence and canonical telemetry remain untouched.
- Deleting a finding never deletes underlying case evidence, collections, timeline records, or graph nodes.

### 3.4 Contradiction Semantics
- Findings explicitly track contradictions, separating `TEMPORAL_ANOMALY` (clock drift, out-of-order sequence) from `STATE_CONTRADICTION` (mutually exclusive states).
- Contradictions remain unresolved until an analyst explicitly reviews and annotates them.

### 3.5 Hypothesis Evaluation & Competing Comparison
- Hypotheses track supporting evidence tags, contradicting evidence tags, and explicit evidence gaps.
- Competing hypothesis comparisons evaluate multiple propositions side-by-side using categorical metric tallies and gap projections without computing fabricated numerical scores.

## 4. API Endpoints

The service exposes 18 REST endpoints registered under `/api/v1/cases/{case_id}/`:

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/cases/{case_id}/findings/workbench` | Full workbench payload (findings, hypotheses, stats) |
| `GET` | `/cases/{case_id}/findings/export` | Deterministic JSON export with Blake2b manifest hash |
| `GET` | `/cases/{case_id}/findings` | List all findings for a case |
| `POST` | `/cases/{case_id}/findings` | Create a new analyst finding |
| `GET` | `/cases/{case_id}/findings/{finding_id}` | Get finding detail with version history |
| `PATCH` | `/cases/{case_id}/findings/{finding_id}` | Edit finding, automatically archiving version |
| `DELETE` | `/cases/{case_id}/findings/{finding_id}` | Soft/hard delete finding without deleting evidence |
| `POST` | `/cases/{case_id}/findings/{finding_id}/evidence` | Attach evidence reference to finding |
| `DELETE` | `/cases/{case_id}/findings/{finding_id}/evidence/{source_id}` | Disassociate evidence reference |
| `POST` | `/cases/{case_id}/findings/{finding_id}/review` | Submit review decision preserving epistemic status |
| `GET` | `/cases/{case_id}/hypotheses/workbench` | List evaluated hypotheses with evidence & gaps |
| `GET` | `/cases/{case_id}/hypotheses/compare` | Multi-hypothesis side-by-side comparison matrix |
| `POST` | `/cases/{case_id}/hypotheses/m74` | Create a hypothesis under investigation |
| `PATCH` | `/cases/{case_id}/hypotheses/m74/{hypothesis_id}` | Update hypothesis statement or status |
| `DELETE` | `/cases/{case_id}/hypotheses/m74/{hypothesis_id}` | Delete hypothesis without deleting evidence |
| `POST` | `/cases/{case_id}/hypotheses/{hypothesis_id}/evidence` | Attach supporting/contradicting evidence tag |
| `DELETE` | `/cases/{case_id}/hypotheses/{hypothesis_id}/evidence/{evidence_tag}` | Remove evidence tag |
| `POST` | `/cases/{case_id}/hypotheses/{hypothesis_id}/gaps` | Record missing telemetry gap |

## 5. Analyst Frontend Experience

Implemented in `apps/desktop/src/features/InvestigationFindingsWorkbench.tsx`.

### 5.1 UI Architecture
- Dense, warm-neutral interface adhering to LogIntel design system:
  - IBM Plex Sans and IBM Plex Mono typography.
  - Charcoal text, subtle borders (`#e0dbd3`), and restrained categorical badges.
  - Sub-views:
    1. **Findings View:** Filterable list with epistemic badge (`OBSERVED`, `INFERRED`, `UNKNOWN`) and review badge (`UNREVIEWED`, `ACCEPTED`, `REJECTED`, `DISPUTED`). Detailed finding panel displaying statement, version history accordion, supporting collections, attached evidence references, and review decision panel.
    2. **Hypotheses View:** Hypothesis cards with categorical status, supporting evidence count, contradicting count, and evidence gap count. Detail view with side-by-side evidence inspection, gap management, and analyst assessment.
    3. **Hypothesis Comparison View:** Matrix comparing competing hypotheses side-by-side across supporting evidence, contradicting evidence, and identified gaps.
    4. **Provenance Inspector:** Inspects source type, source ID, host, timestamp, citation tag, and cryptographic hash for attached evidence.
    5. **Export Facility:** Downloads complete deterministic JSON findings and hypothesis manifest.
