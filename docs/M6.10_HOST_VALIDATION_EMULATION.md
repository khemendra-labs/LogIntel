# LogIntel M6.10: Real-World Host Validation & Adversary Emulation Architecture

## 1. Executive Summary

Milestone **M6.10** establishes the definitive validation, adversarial emulation, and end-to-end verification harness for the LogIntel Advanced Linux Telemetry and Host Intelligence platform (Program M6).

Operating under LogIntel's foundational epistemic invariant:
> *"LogIntel must help an analyst connect evidence, not manufacture certainty."*

M6.10 unites the host telemetry collectors, decoders, normalization pipelines, detection rules, multi-stage attack sequence correlation engines, and unified host graph topology introduced across M6.1 through M6.9 into an automated, non-destructive, and deterministic validation harness.

## 3. Emulated Multi-Stage Adversary Scenarios

### Scenario 1: Web Shell to Root Escalation & Cron Persistence (`web_shell_priv_esc_cron`)
- **Stage 1 (Initial Access & Reconnaissance):**
  - Web application worker (`/usr/sbin/apache2` or `nginx`) spawns interactive shell `/bin/bash`.
  - Process execution telemetry captures command: `/bin/bash -c "id; whoami; uname -a"`.
- **Stage 2 (Interactive C2 Reverse Shell):**
  - Shell establishes outbound socket connection to adversary C2 `198.51.100.200:4444`.
  - Network telemetry identifies outbound socket from unprivileged worker.
  - Triggers detection: `sec.reverse_shell_socket` (MITRE T1059.004, T1071).
- **Stage 3 (Privilege Escalation):**
  - Exploit execution or `sudo` abuse executing `/usr/bin/python3 -c "import os; os.setuid(0); os.system('/bin/sh')"`.
  - Audit telemetry captures UID transition from `33` (www-data) to `0` (root).
- **Stage 4 (Persistence Injection):**
  - Adversary writes hourly cron job payload to `/etc/cron.d/root_backdoor`.
  - Telemetry captures file modification event: `EVENT_TYPE_CRON_MODIFIED`.
  - Triggers detection: `sec.cron_persistence_tamper` (MITRE T1053.003).
- **Stage 5 (Credential Access):**
  - Process executes `/usr/bin/cat /etc/shadow`.
  - High-privilege access audit logged.

### Scenario 2: Container Escape & Host C2 Channel (`container_escape_c2`)
- **Stage 1 (Container Namespace Breakout):**
  - Adversary inside privileged container accesses `/proc/sysrq-trigger` and host namespace descriptors.
  - Spawns host namespace execution via `nsenter --mount=/proc/1/ns/mnt /bin/bash`.
  - Triggers detection: `sec.container_escape_attempt` (MITRE T1611).
- **Stage 2 (In-Memory Stealth Execution):**
  - Adversary downloads binary into memory via `memfd_create("stealth_agent", MFD_CLOEXEC)`.
  - Triggers detection: `sec.memory_execution` (MITRE T1620, T1059).
- **Stage 3 (Systemd Service Persistence):**
  - Drop persistent service definition `/etc/systemd/system/dockerd-sync.service`.
  - Triggers detection: `sec.systemd_persistence_drop` (MITRE T1543.002).
- **Stage 4 (Outbound Encrypted Exfiltration):**
  - Host agent initiates high-volume outbound socket to external destination `203.0.113.88:8443`.
  - Correlated to host entity graph.

### Scenario 3: In-Memory Stealth Execution & Backdoor Listener (`mem_exec_backdoor_listener`)
- **Stage 1 (Kernel Module Tampering):**
  - Adversary invokes `init_module` / `finit_module` to load rootkit `rk_stealth.ko`.
  - Triggers detection: `sec.kernel_module_tampering` (MITRE T1547.006).
- **Stage 2 (Unauthorized Backdoor Listening Socket):**
  - Adversary binds stealth listening socket on unassigned high port `0.0.0.0:31337`.
  - Network telemetry detects listening port outside standard service baseline.
  - Triggers detection: `sec.suspicious_listening_socket` (MITRE T1571).
- **Stage 3 (SSH Authorized Keys Backdoor):**
  - Adversary appends rogue public key to `/root/.ssh/authorized_keys`.
  - Triggers detection: `sec.ssh_authorized_keys_tamper` (MITRE T1098.004).

## 4. Epistemic Integrity and Zero Host Mutation

1. **Strict Epistemic Invariants:**
   - Emulated events and alerts maintain strict distinction between `OBSERVED` facts and `INFERRED` attack patterns.
   - Confidence scoring is bounded: $0.0 \le \text{confidence} \le 1.0$.
   - Adversary campaigns that have missing stages are marked with gaps rather than manufactured linkages.

2. **Zero Host State Mutation:**
   - All adversary emulation is performed purely in-memory via synthetic canonical event telemetry streamed directly to the detection and correlation pipeline.
   - Host readiness verification reads read-only system descriptors without creating, deleting, or altering any live host files, cron jobs, network sockets, or kernel modules.

## 5. API and Client Specifications

### REST Endpoints
- `GET /api/v1/system/host-validation`
  - Runs the full host validation suite across live interfaces and all 3 adversary emulation scenarios.
  - Returns `HostValidationReport`.
- `POST /api/v1/system/host-validation/emulate`
  - Executes a single parameterized adversary scenario on the specified host.
  - Request body: `{"scenario_type": "web_shell_priv_esc_cron", "host": "prod-01"}`.
  - Returns `ScenarioEmulationResult`.

### Desktop Client Library
- `fetchHostValidationReport(): Promise<HostValidationReport>`
- `emulateHostScenario(scenarioType: string, host?: string): Promise<ScenarioEmulationResult>`

All endpoints and client methods require bearer token authentication.
