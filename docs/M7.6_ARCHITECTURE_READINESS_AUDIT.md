## 1. Executive Summary

Milestone M7.6 establishes a structured, evidence-grounded, deterministic forensic reporting, evidence packaging, and case handoff operational layer. This audit inspects the current repository state across milestones M5.3–M5.12, M6.1–M6.10, and M7.1–M7.5 to determine architectural feasibility, reuse boundaries, and persistence constraints prior to any source code modifications.

The primary forensic invariants governing M7.6 are:
1. **The Investigation Trust Hierarchy:**
   $$\text{AUTHORITATIVE EVIDENCE} \neq \text{ANALYST FINDING} \neq \text{HYPOTHESIS} \neq \text{ASSESSMENT} \neq \text{REPORT NARRATIVE} \neq \text{AI DRAFT}$$
2. **Zero Secondary Storage of Authoritative Telemetry:** Reports and evidence packages contain structured references, manifests, citation tags, and cryptographic hashes. They never duplicate raw forensic telemetry into a second authoritative database.
3. **Evidence Immutability:** Authoritative forensic telemetry in `logintel.db` remains 100% read-only.
4. **Epistemic Independence:** Evidence epistemic states (`OBSERVED`, `INFERRED`, `UNKNOWN`) remain independent of report status (`DRAFT`, `REVIEW_READY`, `FINALIZED`), review status (`ACCEPTED`, `DISPUTED`), or handoff status.
5. **Human Analyst Authority:** AI assistance remains strictly advisory and bounded. AI can draft narrative text or summaries but cannot finalize reports, close cases, accept hypotheses, or mutate database state.

## 6. Report Architecture

The report architecture organizes report content into 20 structured typed sections:
1. `case_identification`: Case ID, title, incident reference, owner, status, created/updated timestamps.
2. `investigation_scope`: Systems, hosts, users, time windows, and incident boundaries.
3. `executive_summary`: Concise operational synthesis of the investigation.
4. `investigation_objective`: Analyst question, triggering incident, and inquiry goals.
5. `evidence_sources`: Telemetry sources inspected (e.g., `auth.log`, `auditd`, `syslog`, `network`).
6. `evidence_collections`: M7.3 logical evidence collections included in the investigation.
7. `unified_timeline_summary`: Chronological progression of key observed events and timeline milestones.
8. `key_findings`: M7.4 structured analyst findings (`OBSERVED` / `INFERRED` / `UNKNOWN`).
9. `hypotheses`: M7.4 competing hypotheses with evaluation statuses (`SUPPORTED`, `WEAKENED`, etc.).
10. `threat_hunting_activity`: M7.5 governed hunts executed, parameters, and query fingerprints.
11. `evidence_correlation`: Correlated clusters, multi-host traces, and entity relationships.
12. `case_assessment`: M5.11 categorical case assessment and closure readiness.
13. `evidence_gaps`: Explicitly modeled telemetry omissions (`SOURCE_UNAVAILABLE`, `NO_EVENT_OBSERVED`).
14. `outstanding_questions`: Unresolved investigation questions.
15. `analyst_interpretation`: Subjective analytical commentary clearly distinguished from observed facts.
16. `conclusion_current_assessment`: Current investigative conclusion.
17. `limitations`: Technical, visibility, and scope boundaries of the investigation.
18. `handoff_notes`: Analyst-to-analyst transition instructions and operational notes.
19. `provenance_manifest`: Cryptographic source hashes and reference mappings.
20. `report_metadata`: Version, author, lifecycle state, created/updated timestamps, Blake2b digest.

## 7. Evidence Package Architecture

An evidence package is an exportable, self-contained forensic package:
- **Zero Raw Copying:** Package contains structured JSON/CSV files referencing authoritative source records via `source_type`, `source_id`, and `citation_tag`.
- **Package Manifest:** Contains `package_id`, `case_id`, `report_id`, `report_version`, `created_by`, `created_at`, `included_artifacts`, `source_references`, `provenance_hashes`, and `package_hash` (Blake2b digest).
- **Canonical Ordering:** All references, artifacts, and fields are sorted canonically before hashing to ensure byte-identical reproducibility across runs.

---

## 8. Handoff Architecture

Case handoff transitions operational ownership without concluding or altering the case:
- Communicates investigated scope, verified facts, active hypotheses, evidence gaps, open questions, and recommended next steps.
- Enforces lifecycle: `NOT_READY -> READY_FOR_HANDOFF -> HANDED_OFF -> ACKNOWLEDGED -> RETURNED_FOR_FOLLOWUP`.
- Captures operator identities: `prepared_by`, `reviewed_by`, `handed_off_by`, `acknowledged_by`.
- Preserves complete handoff history in immutable `case_audit_log`.

## 9. AI Boundary & Containment Invariants

Local AI assistance operates under strict DFIR invariants:
- **Advisory Role:** AI generates draft narrative summaries (`AI_GENERATED_DRAFT`).
- **No Autonomous Authority:** AI cannot finalize reports, close cases, accept hypotheses, or mutate evidence.
- **Prompt Injection Containment:** Malicious evidence text or injection strings inside notes/logs are treated as inert string data.
- **Local-Only:** No network egress, no external cloud LLMs, no remote RAG.

## 11. Persistence Boundary & Migration Decision

### **MIGRATION DECISION: ZERO NEW MIGRATIONS REQUIRED.**
- Schema migrations remain frozen at **5** (`schema_migrations` count = 5).
- The existing `case_reports` table in `cases.db` provides:
  `report_id, case_id, version, title, executive_summary, facts_json, inferences_json, hypotheses_json, unknowns_json, recommendations_json, analyst_notes, generated_by, model_id, model_digest, context_version, created_at, is_final`.
- Structured 20-section report models serialize into typed JSON columns (`facts_json`, `inferences_json`, `hypotheses_json`, `unknowns_json`, `recommendations_json`) and structured `analyst_notes` JSON metadata.
- Report revisions insert a new row with incremented `version` (enforced by PK: `case_id, report_id, version`), satisfying immutable version history without modifying prior rows.
- Existing triggers `trg_prevent_case_reports_update` and `trg_prevent_case_reports_delete` preserve historical version immutability.
- Handoff and package lifecycle events are recorded in `case_audit_log` with triggers preventing modification/deletion.
- **Migration 6, 7, 8 are explicitly rejected.**

## 15. Risks & Blockers

- **Risk:** Conflating report finalization with case closure.
  - *Mitigation:* Strict validation logic ensuring report finalization (`FINALIZED`) never transitions case status to `CLOSED`.
- **Risk:** Non-deterministic JSON serialization causing divergent package hashes across runs.
  - *Mitigation:* Enforce `sort_keys=True` and canonical list ordering on all package manifests.
- **Blockers Identified:** **NONE.** Existing architecture, schemas, and primitives fully accommodate M7.6 without technical barriers.
