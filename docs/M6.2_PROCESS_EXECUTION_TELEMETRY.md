## 1. Overview & Architectural Mission

Prior to M6.2, LogIntel's visibility into host process execution was strictly indirect: process execution was observed only when a privileged user invoked a command via `sudo` (`SUDO_COMMAND` in `auth.log`), or when AppArmor registered a mandatory access control policy denial in `kern.log`. General unprivileged execution (`/bin/sh`, Python scripts, network reconnaissance tools, automated cron jobs, background workers, or persistence payloads) was invisible to the platform.

Milestone M6.2 introduces high-fidelity, deterministic, forensic-safe process and execution telemetry using the host's native Linux audit subsystem (`auditd`):

```text
REAL LINUX PROCESS
       ↓ (execve / clone / syscall / session)
LINUX KERNEL AUDIT SUBSYSTEM
       ↓
/var/log/audit/audit.log
       ↓
AuditLogCollector (FileTailer with inode/offset tracking & audit_id grouping)
       ↓
AuditParser (EXECVE decoding, PROCTITLE decoding, SYSCALL/PAM session parsing)
       ↓
CanonicalEvent (with deterministic SHA-256 fingerprint & credential masking)
       ↓
Forensic Database (logintel.db events table, idempotent ingestion)
       ↓
ProcessAncestryResolver (deterministic parent-child SPAWNED graph reconstruction)
       ↓
M5 Investigation Intelligence (Cases, Hypotheses, Timeline, Advisory AI)
```

## 2. Linux Auditd Subsystem Integration

### 2.1 Privilege Architecture
Unlike eBPF or intrusive kernel modules that require `CAP_BPF` or `CAP_SYS_ADMIN`, Ubuntu Linux configures `/var/log/audit/audit.log` with permissions `-rw-r----- 1 root adm`. 
Because standard LogIntel deployment users belong to group `adm` (gid 4), **LogIntel ingests comprehensive process and execution telemetry with ZERO root privilege escalation**. The application desktop, API server, and ingestion daemon run completely unprivileged.

### 2.2 Host Audit Rule Configuration
Audit records are recorded according to host audit rules:
- **Default Workstation State:** Even with no custom audit rules configured, Linux auditd records `PROCTITLE`, `LOGIN`, `USER_START`, `USER_END`, `CRED_ACQ`, `SERVICE_START`, and `SERVICE_STOP` for background jobs and cron executions.
- **Recommended Sysadmin Audit Rule:** To enable full syscall-level command line capturing (`EXECVE` with complete `argc` and `a0`..`aN` arguments) across all processes, administrators may deploy the following non-intrusive rule:
  ```bash
  auditctl -a always,exit -F arch=b64 -S execve,execveat -k process_exec
  ```
- **Forensic Coverage Invariant:** M6.2 never converts absence of an audit record into proof that no execution occurred. The telemetry state explicitly distinguishes `AUDIT RECORD AVAILABLE` from `AUDIT RULE NOT CONFIGURED` from `AUDIT SOURCE UNAVAILABLE`.

## 3. Collector Architecture: `AuditLogCollector`

Implemented in `apps/engine/src/logintel/collectors/audit.py`, `AuditLogCollector` subclasses `Collector`:
- **Stateful File Tailing:** Leverages `FileTailer` to track `byte_offset` and `current_inode` in SQLite `ingestion_state`.
- **Log Rotation Awareness:** Detects logrotate file replacements (`audit.log` $\rightarrow$ `audit.log.1`) via inode modification or file truncation, resetting byte offset safely to 0 without skipping or duplicating records.
- **Multi-Record Audit Grouping:** Linux auditd outputs related records for a single event in adjacent lines sharing the exact same `msg=audit(epoch.msec:sequence)`. `AuditLogCollector` streams and buffers lines matching the same `audit_id`, merging them into a coherent `RawRecord` with all contributing lines and byte offsets preserved.

## 4. Parser Architecture: `AuditParser`

Implemented in `apps/engine/src/logintel/parsers/audit.py`, `AuditParser` specializes in Linux audit grammar:

### 4.1 Supported Audit Record Types
1. **`SYSCALL`:** Extracts PID, PPID, UID, GID, EUID, EGID, AUID, session ID (`ses`), process name (`comm`), executable (`exe`), syscall number, architecture, exit code, and terminal (`tty`).
2. **`EXECVE`:** Extracts argument count (`argc`) and indexed arguments (`a0`, `a1`... `aN`). Decodes hex-encoded values and unescapes arguments to reconstruct the complete invoked command line.
3. **`PROCTITLE`:** Decodes hex-encoded null-delimited process titles (e.g. `2F7573722F7362696E2F43524F4E002D66002D50` $\rightarrow$ `/usr/sbin/CRON -f -P`).
4. **`USER_START` / `USER_END`:** Normalizes PAM session lifecycle events (`op=PAM:session_open`, `acct="root"`, `res=success`) into `AUDIT_SESSION_START` and `AUDIT_SESSION_END`.

### 4.2 EXECVE and PROCTITLE Hex Decoding
Auditd encodes arguments containing spaces, quotes, or non-printable characters as pure hexadecimal ASCII strings without delimiters. `AuditParser` implements `decode_audit_hex`:
- Identifies unquoted even-length hex strings.
- Safely decodes UTF-8 bytes with replacement fallback for invalid bytes.
- Converts null byte delimiters (`\x00`) to spaces.
- Clamps decoded output to `MAX_COMMAND_LINE_LENGTH` (8,192 chars) with `[TRUNCATED]` markers.

## 5. Credential & Sensitive Data Handling

Command lines frequently contain sensitive credentials passed via command-line flags. To safeguard forensic integrity while protecting analysts and AI systems from credential exposure, LogIntel enforces a strict separation:

```text
RAW AUDIT RECORD (Retained unaltered in raw_message & SQLite raw_message column)
       ↓
SENSITIVE DATA SANITIZER (mask_credentials in sanitizer.py)
       ↓
CANONICAL COMMAND LINE (process.command_line = masked string)
       ↓
DISPLAY & ADVISORY REPRESENTATION (summary = masked summary; AI context receives masked text)
```

### Sanitization Patterns
`mask_credentials` deterministically conceals:
- `--password=VALUE` and `--password VALUE` $\rightarrow$ `--password=[MASKED]`
- `--token=VALUE`, `--api-key=VALUE`, `--secret=VALUE` $\rightarrow$ `[MASKED]`
- `Authorization: Bearer VALUE` $\rightarrow$ `Authorization: Bearer [MASKED]`
- `mysql -u root -p VALUE` $\rightarrow$ `mysql -u root -p [MASKED]`

### False-Positive Protection
Legitimate operational flags are preserved without masking:
- Port specifications: `ssh -p 22`, `nmap -p 80,443` (preserved)
- Directory flags: `mkdir -p /path/to/dir` (preserved)

## 6. Process Identity & PID Reuse Protection

Linux kernel process IDs wrap around continuously. To prevent a subsequent process reusing a PID from attaching to an earlier process's investigation tree:
`build_process_identity(host, pid, timestamp, exe, audit_seq)` derives a collision-free identity key:
```text
proc:<host>:<pid>:<iso_timestamp>:<executable_basename>:seq<audit_seq>
```
Example:
`proc:Khemendra-labs:75899:2026-10-06T03:05:01.300000+00:00:cron:seq699`

## 7. Process Ancestry Reconstruction

Implemented in `apps/engine/src/logintel/correlation/ancestry.py`, `ProcessAncestryResolver` reconstructs execution hierarchies (`parent -> child -> grandchild`):
- Traces from a target process backwards in time through `process_ppid`.
- Requires `timestamp <= current_event.timestamp` to ensure proper temporal ordering.
- Strictly adheres to epistemic rules:
  - `OBSERVED`: Explicit `ppid` with matching parent event record $\rightarrow$ `SPAWNED` relationship (`DIRECT` confidence).
  - `UNKNOWN`: Missing or zero `ppid` $\rightarrow$ marked `UNKNOWN`, never manufactures artificial relationships.
- Prevents infinite recursion via visited PID tracking and depth bounding (`MAX_ANCESTRY_DEPTH = 32`).

## 8. Forensic Database & Schema Boundary

- **Migration 6 Absent:** In accordance with the M6 strategic charter, **Migration 6 was NOT created**.
- **Schema Compatibility:** The existing `events` SQLite table (Migration 1) already possesses first-class columns for `process_name`, `process_pid`, `process_ppid`, `process_executable`, `process_command_line`, `username`, `uid`, `session_id`, `terminal`, and `metadata_json`. All deep audit attributes serialize into `metadata_json` without modifying database constraints.
