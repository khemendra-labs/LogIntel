## 1. Architectural Mission & Core Invariants

Milestone M7.3 delivers the second major analyst-facing investigation capability of Program M7:
> **Logical Evidence Collections and a dedicated Forensic Evidence Workbench for organizing, reviewing, correlating, annotating, and exporting evidence references within an investigation.**

### Fundamental Axiom:
```text
Evidence Collection  ≠  Copy of Evidence
```

An Evidence Collection is an **analyst organization layer**, not a new authoritative evidence layer.

### Core Invariants:
1. **Zero Evidence Duplication:**
   - Adding evidence to a collection stores only a reference to the authoritative record (`source_type`, `source_id`, `epistemic_status`, `collection_status`).
   - Raw event payloads, canonical logs, and forensic telemetry are never copied, altered, or rewritten.
2. **Preservation of Epistemic & Review States:**
   - Epistemic states (`OBSERVED`, `INFERRED`, `UNKNOWN`) reflect objective forensic provenance and are strictly immutable when referenced.
   - Review states (`UNREVIEWED`, `ACCEPTED`, `REJECTED`, `DISPUTED`) are decoupled; organizing an item into a collection does not automatically promote or alter its review status.
3. **Deletion Semantics:**
   - Removing an item from a collection deletes only the organizational membership link; the underlying authoritative evidence and canonical event remain intact.
   - Deleting a collection deletes only the analyst grouping; all underlying evidence items remain permanently preserved in the case and forensic database.
4. **Authoritative Forensic Telemetry Immutability:**
   - `logintel.db` remains 100% read-only throughout all workbench and collection operations.
   - `cases.db` maintains append-only audit records for all collection operations.
5. **Strict Case Isolation:**
   - All collection queries, mutations, exports, and searches are strictly case-scoped. Cross-case reference leakage is prevented by authoritative case boundary checks.

## 2. Evidence Collection Domain Model

Implemented in `apps/engine/src/logintel/collections/models.py`.

### 2.1 Collection Lifecycle & Status
```python
class EvidenceCollectionStatus(str, Enum):
    ACTIVE = "ACTIVE"
    ARCHIVED = "ARCHIVED"
```
The minimal lifecycle strictly uses `ACTIVE` and `ARCHIVED`. Operational statuses such as `OPEN` or `CLOSED` are avoided to prevent duplicating case lifecycle semantics.

### 2.2 Evidence Item Structure
```python
class EvidenceCollectionItem(BaseModel):
    item_id: str
    collection_id: str
    case_id: int
    source_type: str                   # "canonical_event" | "detection" | "alert" | "incident" | "timeline_item" | "host_telemetry" | "graph_relationship"
    source_id: str
    role: EvidenceItemRole             # PRIMARY, SUPPORTING, CONTEXTUAL, CORROBORATING, CONTRADICTING, TEMPORAL, ENTITY_LINK
    epistemic_status: EpistemicStatus  # OBSERVED | INFERRED | UNKNOWN
    collection_status: CollectionStatus # SOURCE_AVAILABLE | RULE_NOT_CONFIGURED | NO_EVENT_OBSERVED | TELEMETRY_DROPPED | UNKNOWN
    analyst_annotation: Optional[str] = None
    ordering_weight: int = 0
    added_by: str = "analyst"
    added_at: str
    source_metadata: Dict[str, Any] = Field(default_factory=dict)
```

### 2.3 Collection Container Structure
```python
class EvidenceCollection(BaseModel):
    collection_id: str
    case_id: int
    title: str
    description: Optional[str] = None
    status: EvidenceCollectionStatus = EvidenceCollectionStatus.ACTIVE
    tags: List[str] = Field(default_factory=list)
    analyst_metadata: Dict[str, Any] = Field(default_factory=dict)
    items: List[EvidenceCollectionItem] = Field(default_factory=list)
    created_by: str = "analyst"
    created_at: str
    updated_at: str
```

## 3. Evidence Workbench Architecture

The Evidence Workbench service is implemented in `apps/engine/src/logintel/collections/service.py` (`EvidenceWorkbenchService`).

### 3.1 Multi-Layer Evidence Aggregation & Projection
When an analyst opens the Evidence Workbench for a case, the workbench projects all authoritative evidence across:
- Case evidence references (`case_evidence_references`)
- Operational incident alerts (`alerts` for the incident)
- Reconstructed attack-path relationships (`AttackGraphVisualizer` and topological paths)
- Unified timeline items (`timeline_service`)
- Detection rules fired for the incident

Every resolved item exposes full provenance:
```text
Evidence Item ID
Source Layer & ID
Host ID & Timestamp
Epistemic Status (OBSERVED / INFERRED / UNKNOWN)
Collection Status
Hash / Content Fingerprint
Related Entities & ATT&CK Tactics
Original Source Pointer
```

### 3.2 Duplicate Membership Idempotency
Adding the same evidence reference multiple times to the same collection is deterministic and idempotent:
- The service detects existing membership by `(collection_id, source_type, source_id)`.
- If already present, it returns the existing item without creating duplicate rows or altering the created timestamp.

### 3.3 Re-Ordering & Ordering Semantics
- Members maintain an explicit `ordering_weight` integer.
- Analysts can reorder items within a collection.
- Re-ordering affects solely presentation within the collection; source event chronological order is never mutated.

## 4. API Endpoints

Registered in `apps/engine/src/logintel/api/routes.py`:

| Method | Endpoint | Description |
| :--- | :--- | :--- |
| `GET` | `/api/v1/cases/{case_id}/evidence/collections` | List all collections for a case |
| `POST` | `/api/v1/cases/{case_id}/evidence/collections` | Create a new evidence collection |
| `GET` | `/api/v1/cases/{case_id}/evidence/collections/{collection_id}` | Retrieve collection with members |
| `PATCH` | `/api/v1/cases/{case_id}/evidence/collections/{collection_id}` | Update title, description, tags, status |
| `DELETE` | `/api/v1/cases/{case_id}/evidence/collections/{collection_id}` | Delete collection (references removed, evidence preserved) |
| `POST` | `/api/v1/cases/{case_id}/evidence/collections/{collection_id}/items` | Add evidence reference to collection |
| `PATCH` | `/api/v1/cases/{case_id}/evidence/collections/{collection_id}/items/{item_id}` | Update analyst annotation or ordering weight |
| `DELETE` | `/api/v1/cases/{case_id}/evidence/collections/{collection_id}/items/{item_id}` | Remove reference from collection |
| `GET` | `/api/v1/cases/{case_id}/evidence/workbench` | Multi-layer evidence listing with filtering and search |
| `GET` | `/api/v1/cases/{case_id}/evidence/collections/{collection_id}/export` | Deterministic case-scoped export (`format=json` or `csv`) |

All endpoints enforce bearer authentication, case authorization, input sanitization, and bounded pagination.
