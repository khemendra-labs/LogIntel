## 1. Executive Summary

Milestone 5.6 implements an evidence-grounded, deterministic **Investigation Intelligence Layer** on top of the verified M5.5 persistent case management architecture. ## 6. Investigation Findings

Findings represent structured units of intelligence derived during an investigation.
* **Epistemic Status:** Every finding explicitly declares whether it is `OBSERVED` (directly witnessed in authoritative forensic events), `INFERRED` (derived via deterministic correlation or attack-path graph), or `UNKNOWN` (hypothesized or missing verification).
* **Confidence Basis:** Stated in concrete, evidence-backed terms (e.g., `AUTHORITATIVE_EVENT_DIRECT_MATCH`, `CORRELATED_MULTI_ALERT_CLUSTER`) rather than model probabilities.
* **Provenance:** Retains `source_references`, `related_entities`, `related_alerts`, `related_detections`, `related_events`, and `generated_by`.

---

## 7. Correlation Engine

The correlation engine identifies multi-attribute linkages between forensic entities and evidence items:
* Multi-attribute checks: `SAME_HOST`, `SAME_USER`, `SAME_SOURCE_IP`, `SAME_DEST_IP`, `SAME_PROCESS`, `SAME_COMMAND`, `SAME_AUTHENTICATION_IDENTITY`, `SAME_INCIDENT`, `SAME_ALERT`, `SAME_DETECTION`, `TEMPORAL_PROXIMITY`.
* Corroborating reasons: Every correlation outputs an explicit list of human-readable reasons and numeric temporal delta (in seconds).
* No black-box or unexplained linkages are emitted.

---

## 8. Temporal Intelligence

Anchor-based temporal investigation allows analysts to examine telemetry:
* `BEFORE` window (e.g., 300 seconds prior to anchor)
* `DURING` window (anchor timestamp ± margin)
* `AFTER` window (e.g., 300 seconds post anchor)
* **Epistemic Distinction:** Distinguishes between `TEMPORAL_ANOMALY` (out-of-sequence timestamps, clock drift) and `STATE_CONTRADICTION` (logically mutually exclusive states occurring simultaneously).

---

## 9. Evidence Gaps

The evidence gap engine inspects the case scope and evidence set to deterministically identify missing telemetry:
* Gap types detected: `MISSING_AUTHENTICATION_TELEMETRY`, `MISSING_PROCESS_TELEMETRY`, `MISSING_NETWORK_TELEMETRY`, `MISSING_DNS_TELEMETRY`, `INSUFFICIENT_TEMPORAL_COVERAGE`, `UNRESOLVED_ENTITY`, `INSUFFICIENT_CORROBORATION`.
* Governed Query Suggestion: Recommends safe, allowlisted threat-hunting queries designed to close the gap.
* Strict Safeguard: Gap recommendations **never** execute automatically. Execution requires explicit analyst review and approval.

---

## 10. Threat Hunting Workflow

M5.6 replaces ad-hoc querying with a governed 6-stage lifecycle:
```text
Analyst/AI Suggestion → Query Proposal → Semantic & Parameter Validation → Analyst Preview → Explicit Approval → Governed Execution
```
1. **Allowlisted Query Templates:** Only predefined templates are supported (`HUNT-AUTH-USER`, `HUNT-PROC-EXEC`, `HUNT-NET-CONNS`, `HUNT-DNS-LOOKUP`, `HUNT-FILE-ACCESS`, `HUNT-IP-ACTIVITY`).
2. **Fixed SQL Structure & Parameterized Binding:** Parameterized allowlisted query templates are the primary SQL-injection control. Parameters are bound separately via SQLite placeholder (`?`) parameter binding. Pattern rejection is defense-in-depth and is not relied upon as the security boundary.
3. **Execution Guard:** Execution requests with `approved=False` or invalid parameters are rejected with HTTP 400.
4. **Audit Logging:** Every execution is permanently recorded in `cases.db.case_query_history`.

---

## 11. Query Result Differentiation

Query executions classify outcomes into distinct operational states:
* `MATCHED`: Matching authoritative events found.
* `NO_MATCH`: Query executed successfully; no matching events found in current scope. *(Explicitly preserved: `NO_MATCH` does not prove an event never occurred).*
* `PARTIAL`: Result limit reached; further pagination required.
* `UNAVAILABLE`: Telemetry source not collected or table empty.
* `INVALID`: Parameter validation failed or disallowed tokens detected.
* `FAILED`: Internal database error.

## 12. Entity Investigation (Pivots)

Entity pivots enable deep investigation into any key (`IP`, `USER`, `HOST`, `PROCESS`, `COMMAND`, `FILE`, `INCIDENT`, `ALERT`, `DETECTION`):
* Gathers related incidents, alerts, forensic events, and graph relationships from `logintel.db`.
* Zero duplication: Raw forensic event payloads are queried on demand and referenced by ID; they are not duplicated into `cases.db`.

---

## 13. Timeline Integration

Unifies heterogeneous artifacts into a chronological sequence:
* Consolidates forensic events, operational alerts, detections, analyst notes, and attack path steps.
* Provenance tracking: Every timeline entry is tagged with its `source_type` (`OBSERVED_EVENT`, `DETECTION`, `ANALYST_NOTE`, `DERIVED_CORRELATION`, `AI_INTERPRETATION`) and a boolean `is_authoritative` flag.
* AI interpretations and derived correlations are never rendered as authoritative events.

---

## 14. Hypothesis Analysis

Extends M5.5 persistent hypotheses with deterministic corroboration analysis:
* Evaluates supporting evidence, contradicting evidence, evidence gaps, temporal consistency, and related threat-hunt query results.
* Evaluates support matrix:
  - `SUPPORTED BY CURRENT EVIDENCE`: Direct supporting evidence, no contradicting evidence.
  - `WEAKLY SUPPORTED`: Corroborating evidence present but lacks direct forensic proof.
  - `CONTRADICTED`: Direct contradicting evidence identified.
  - `INSUFFICIENT EVIDENCE`: Zero supporting or corroborating evidence.
  - `UNRESOLVED`: Complex mixed evidence.
* **Analyst Ownership:** The engine **never** silently alters the analyst's chosen hypothesis status (`OPEN`, `VALIDATED`, `REFUTED`, `ABANDONED`). The analysis remains strictly an advisory evaluation.

## 29. Known Limitations

1. **Local Workstation Scale:** The correlation and timeline intelligence engines execute in-memory against local SQLite queries. While sub-10ms for investigations containing thousands of events, large-scale investigations involving millions of events will require database-level index optimizations or paging.
2. **Governed Threat Hunt Allowlist:** The query template catalog is restricted to six core templates (`HUNT-AUTH-USER`, `HUNT-PROC-EXEC`, `HUNT-NET-CONNS`, `HUNT-DNS-LOOKUP`, `HUNT-FILE-ACCESS`, `HUNT-IP-ACTIVITY`). Queries outside these templates must be proposed and vetted through schema extensions.
3. **Application-Level AI Containment:** Local LLM outputs are contained via application-level boundary prompts and structured schema parsing. The model cannot alter system state, but creative adversarial prompts in evidence text could still cause the model to emit confused advisory text within its allocated response fields.
